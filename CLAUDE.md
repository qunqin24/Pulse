# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Pulse is a macOS menu-bar app: a floating AI usage monitor. SwiftUI renders the UI; a transparent, non-activating AppKit `NSPanel` anchors it to a side of the screen. It tracks three coding agents — Claude Code, Codex and Antigravity — reading each one's real limits by whatever route that agent offers. There is no backend and no account of its own.

## Commands

```bash
swift run Pulse         # build and run
swift build             # type-check everything, previews included
./Scripts/bundle.sh     # assemble build.noindex/Pulse.app (add --zip for a release)
./Scripts/dmg.sh        # the same, wrapped in build.noindex/Pulse-<version>.dmg
./Scripts/check-localization.sh   # the .strings files agree, and every key the source asks for exists
```

**`xcode-select` must point at Xcode, not CommandLineTools.** The `#Preview`
macro is expanded by a plugin that ships with Xcode; without it every build
fails with `PreviewsMacros plugin not found`. Check with `xcode-select -p`, and
fix a wrong one with:

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

(`DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift build` works
as a one-off if you can't change the system setting.) Do **not** "fix" this by
stripping the `#Preview` blocks before building: that produces a clean build
while leaving errors inside those blocks completely unreported, which has
already shipped a broken build to the user once.

**A clean `swift build` is not the same check Xcode runs.** Actor-isolation
mistakes can come out as warnings here and as hard errors in Xcode, where they
fail the whole module and every other file then reports "cannot find type X in
scope" — a wall of noise pointing anywhere but the cause. That has happened
once already, from a nonisolated helper reaching for a constant on a SwiftUI
`View` (every `View` is `@MainActor`). Before saying a change builds:

```bash
swift build -Xswiftc -swift-version -Xswiftc 6
```

and treat any remaining warning as a failure.

The package requires macOS 14+ and Swift tools 6.0 (see [Package.swift](Package.swift)). It can also be opened directly in Xcode via `Package.swift`. There is no test target and no linter configured.

## Shipping

There is no Xcode project, on purpose — Pulse is a plain package, and
[Scripts/bundle.sh](Scripts/bundle.sh) is what turns its bare executable into
something macOS treats as an app. That is not tidiness: **without a bundle
there is no `Bundle.main`**, which means no version number to compare against
(so no update check), no `SMAppService` login item (hence the launch-agent
fallback in [LoginItem.swift](Sources/Pulse/LoginItem.swift)), and nothing to
hand anyone but a build folder.

- **Pushing a tag is the whole release.**

  ```bash
  # CHANGELOG.md first — see below. Then:
  echo 1.0.1 > VERSION && git commit -am "Pulse 1.0.1"
  git tag v1.0.1 && git push && git push origin v1.0.1
  ```

  **[CHANGELOG.md](CHANGELOG.md) needs a `## 1.0.1` section before the tag
  goes up**, and the run stops without one — *before* it builds or publishes,
  so a forgotten entry costs a re-tag rather than a release whose notes went
  out wrong. They are not decoration: the same words are the top of the GitHub
  release *and* the text Sparkle shows in the update window of every installed
  copy, so this is the one part of a release nobody else can write for you. The
  fallback to commit subjects in [Scripts/appcast.py](Scripts/appcast.py) is
  for older versions and hand runs, not for this.

  [`.github/workflows/release.yml`](.github/workflows/release.yml) builds,
  packages and publishes, then signs the archive and commits the Sparkle feed;
  [`ci.yml`](.github/workflows/ci.yml) runs the same build on every push. The
  release needs one secret, `SPARKLE_PRIVATE_KEY`, and fails loudly without it
  rather than publishing a version no installed copy would ever be offered. Both pin **`macos-26`** rather than `macos-latest`,
  because `PanelSurface`'s Liquid Glass needs the macOS 26 SDK to compile at
  all even though it is behind an `#available` check — an older image cannot
  build the package, so both workflows check `xcrun --show-sdk-version` first
  and fail with that sentence instead of a hundred lines of "cannot find
  glassEffect". Warnings fail the build, for the reason at the top of this
  file.   **The tag is checked against `VERSION`** and a mismatch fails the run: ship
  them out of step and every installed copy is told, forever, that an update is
  waiting. A tag with a suffix (`v1.1.0-beta.1`) is published as a pre-release,
  which GitHub's "latest release" excludes — and so, therefore, does the update
  check.
- The version lives in [VERSION](VERSION) and nowhere else. Tag the release
  `v$(cat VERSION)`: the update check reads GitHub's latest release tag and
  compares it against `CFBundleShortVersionString`, so the two have to agree.
- The package's resource bundle must land in `Contents/Resources` —
  `Bundle.module` looks there through `Bundle.main.resourceURL`. Leave it out
  and the app runs, silently in English, with no provider marks.
- `LSUIElement` must be **true**. The code also sets `.accessory`, but that runs
  after the Dock has already been told what to show, so without the key a Dock
  icon appears for a moment at every launch.
- Built for both architectures (`--arch arm64 --arch x86_64`), so one download
  runs everywhere, and zipped with `ditto`, not `zip` — a plain zip flattens the
  symlinks in a bundle and the unzipped copy won't launch.
- **The output directory is named `build.noindex/` for a reason.** Spotlight
  indexes an `.app` wherever it finds one, so a build sitting in the project
  folder turns up in Launchpad and search beside the installed copy — two
  identical Pulses with no way to tell them apart. Worse, whichever one is
  *opened* claims the login item and rewrites Claude Code's status line path to
  itself, so deleting the build later breaks both.
  A `.noindex` suffix is the convention Spotlight honours and the one Xcode's
  own DerivedData relies on. A `.metadata_never_index` marker file was tried
  first and did **not** work — the build was indexed anyway — so the marker is
  kept as a second line but the directory name is what does the job. Don't
  rename it back.
- **The disk image is the install guide** ([Scripts/dmg.sh](Scripts/dmg.sh)).
  Because Pulse isn't notarised, macOS blocks the first launch and the user has
  to allow it by hand — and on macOS 15 and later the old Control-click → Open
  bypass is gone, so it can only be done in System Settings › Privacy & Security
  › Open Anyway. Instructions that live only in a README are instructions nobody
  downloading an app ever reads, so they are printed on the window itself.
  Finder stores the window's size, backdrop and icon positions in a `.DS_Store`,
  and AppleScript is the only way to *write* one — which needs a logged-in
  desktop and permission to drive Finder, neither of which a CI runner has. So
  the layout is captured once on a real Mac
  ([Scripts/dmg-DS_Store](Scripts/dmg-DS_Store)) and copied into the staging
  folder, and the build touches Finder only when that file is missing. Verified
  identical both ways. Re-capture it with `./Scripts/dmg.sh --relayout` after
  changing the backdrop or the icon positions, and commit the result. Note Finder's window `bounds` **include the title bar**,
  so the window is 28pt taller than the 660×420 backdrop or its bottom line is
  cut off. The backdrop is [Scripts/dmg-background.tiff](Scripts/dmg-background.tiff),
  carrying a 1x and a 2x representation; replace the file to redesign it.
- The ad-hoc signature is **not** distribution signing. It stops macOS calling
  the bundle damaged when it is moved; it does nothing for Gatekeeper, which
  will still warn on first open until there is a Developer ID and notarisation.

**Running from a bundle moves the `UserDefaults` domain**, and that is the sharp
edge of this whole change. `UserDefaults.standard` writes to a domain named
after the bundle identifier, or — with no bundle — after the process name. So
every loose `swift run` build has been keeping its settings in a domain called
`Pulse`, and `Pulse.app` reads an empty one: panel position, enabled providers,
language, *and the flag that says opening at login was already decided*. It
would look like a fresh install and would switch login-at-start back on for
someone who had turned it off.
[LegacyDefaults.swift](Sources/Pulse/LegacyDefaults.swift) copies the old domain
across once, taking only keys the new domain doesn't already have. After that
the two diverge, which is right: an Xcode build and an installed `Pulse.app` are
two copies of the app and shouldn't edit each other's settings.
`LoginItem.adoptBundleIfNeeded` is the same problem in the other direction — a
launch agent left over from a loose build still names the old binary, so at the
next login launchd starts the old build *and* `SMAppService` starts the new one.

**Updates install themselves, through Sparkle**
([AppUpdate.swift](Sources/Pulse/AppUpdate.swift)). The thing that makes this
safe without an Apple Developer ID is the **EdDSA key**: Sparkle refuses any
archive not signed by the private half of the key whose public half is in
`Info.plist`, whoever served it. Apple's signing and notarisation are
*recommended* by Sparkle rather than required — that was got wrong here once,
and the mistake cost a whole release cycle of "wait until there's a Developer
ID". The one thing notarisation would fix, Gatekeeper blocking the **first**
launch, is not something any updater can help with.

**The update window's notes are carried in the feed, not fetched from GitHub.** They used to be a `sparkle:releaseNotesLink` pointing at the release page — which is not a link the user clicks: Sparkle loads it into a WebView *inside* the update window, so the whole GitHub page, navigation and all, was rendered in a small panel, and showed nothing at all without a network. The item carries a `<description>` instead, and the link has to be **removed** for it to be used: `releaseNotesLink` takes precedence when both are present.
What goes in it is hand-written, in [CHANGELOG.md](CHANGELOG.md), and [Scripts/changelog.py](Scripts/changelog.py) converts the one version's entry to HTML for the feed while [`release.yml`](.github/workflows/release.yml) puts the same markdown at the top of the GitHub release — one source, so the two cannot drift. Generating it from commit subjects was tried and is wrong: this repository takes direct commits, so the range runs to forty subjects a release and half of them say things like "Update README". That path is kept only as a fallback, so a forgotten entry ships something rather than an empty dialog. The converter knows bullets, `**bold**`, `` `code` `` and links, and nothing else — the file is ours, so its grammar can be small enough to be sure of.
The description carries **spacing only, no colours and no fonts**: Sparkle injects `ReleaseNotesColorStyle.css`, which turns the text white under `prefers-color-scheme: dark` and leaves the background transparent so the window shows through. A feed that brings its own palette fights that and loses in whichever appearance it guessed wrong about — verified by rendering the description in a `WKWebView` with Sparkle's own stylesheet applied, in both appearances.

The private key lives only in the `SPARKLE_PRIVATE_KEY` repository secret;
`Scripts/sparkle-public-key.txt` holds the public half and is meant to be
committed. [Scripts/appcast.py](Scripts/appcast.py) signs each release's zip
and appends an entry to [appcast.xml](appcast.xml), which the release workflow
commits back to `main` — **after** publishing, since the feed points at the
release's own asset and committing first would advertise a 404. Sparkle updates
from the **zip**, not the disk image; the image is for people, the zip is for
the updater.

Three things about the Swift side. `AppUpdate` starts nothing unless
`SUFeedURL` is present, which is only true in a bundle — Sparkle's framework is
in `Contents/Frameworks` and a `swift run` build has neither, so starting it
there would log complaints about a missing feed forever. Sparkle's delegate is
an `@objc` protocol and so cannot be main-actor-isolated, which is why
`UpdaterRelay` sits between it and the `@Observable` model rather than
`AppUpdate` conforming directly. And `didAbortWithError` fires for benign
reasons too — the user closing Sparkle's window is one — so only a genuine
failure to reach or read the feed is reported as one, on the single row that
exists to tell the truth about that.

**Embedding the framework is the fiddly part of the bundle.** SwiftPM links
against Sparkle but has no app to put it in, so `Scripts/bundle.sh` copies it
into `Contents/Frameworks` and adds `@executable_path/../Frameworks` to the
executable's rpath — SwiftPM only ever pointed that at the build directory, and
without the addition the app launches straight into a dyld failure. Signing then
has to run inside out: Sparkle brings nested bundles of its own (XPC services
and its updater app), and signing a container before its contents invalidates
the container.

Note the settings group that holds the *usage* refresh interval is called
"Refresh", not "Updates". It was "Updates" until the app had updates of its own.

## Architecture

Single executable target `Pulse` at [Sources/Pulse](Sources/Pulse), no internal modules — everything lives in one flat directory with one SwiftUI view per file.

**App shell (AppKit-driven, not SwiftUI's WindowGroup):**
- [PulseApp.swift](Sources/Pulse/PulseApp.swift) — `@main` entry. Declares only a `MenuBarExtra` scene, which is a plain two-item menu (Settings, Quit); usage itself is shown solely in the floating panel, which is *not* a SwiftUI scene.
- [AppDelegate.swift](Sources/Pulse/AppDelegate.swift) — sets the app's activation policy to `.accessory` (no Dock icon) and owns the app's long-lived objects: `AppSettings`, `PanelPlacement`, the `FloatingPanelController`, and the settings window.
- [SettingsWindowController.swift](Sources/Pulse/SettingsWindowController.swift) — a hand-rolled `NSWindowController` rather than SwiftUI's `Settings` scene, because an `.accessory` app has to call `NSApp.activate` itself or the window opens behind everything else. It uses `.fullSizeContentView` so content is blurred away under the title bar as it scrolls rather than being clipped at a hard edge, and **the title bar must stay opaque** for that (`titlebarAppearsTransparent = false`, `titlebarSeparatorStyle = .automatic`): transparent plus full-size content means nothing draws up there, so scrolled content came through and printed over "Pulse Settings". No padding is needed — AppKit reports the bar as a 52pt top safe area and the scroll view already insets by it. Note the sidebar does **not** extend behind the traffic lights, and can't be made to here: that is AppKit's treatment of an `NSSplitViewController` sidebar item, which a SwiftUI `NavigationSplitView` in an `NSHostingView` doesn't get — measured with and without both `.fullSizeContentView` and a unified `NSToolbar`.
  **Clicking away from the key field ends its editing, and that is the window's job** (`SettingsWindow.sendEvent`). A macOS text field keeps first responder until another view asks for it, and nothing else in this window ever does — so the field held its focus ring wherever else you clicked, and only switching pane let it go. The test is geometry against the field being edited, never `hitTest`: a hosted SwiftUI tree answers that unreliably (see the panel's drag note), and "was the press inside that box" needs nothing more.
- [FloatingPanelController.swift](Sources/Pulse/FloatingPanelController.swift) — imperative AppKit controller that owns a custom `NSPanel` subclass (`FloatingPanel`, borderless/non-activating, `canBecomeKey`/`canBecomeMain` both `false`) hosting a SwiftUI view tree via `NSHostingView`. It manually computes and animates the panel's frame (collapsed vs. expanded width, pinned to the right edge of `NSScreen.main`) — SwiftUI has no layout say over the panel's outer size; **any expand/collapse animation is driven by `NSAnimationContext`/`panel.animator()` here, not by SwiftUI transitions.**
  **The panel stays out of other apps' full-screen Spaces by default.** This is a window collection behavior, not a guessed full-screen detector: `AppSettings.hidesInFullScreen` selects `.fullScreenNone`, while turning the setting off selects `.fullScreenAuxiliary`. Both retain `.canJoinAllSpaces` for ordinary desktop Spaces. Keep this on the public AppKit behavior — checking other apps' windows would require permissions and would confuse maximized windows with real full-screen Spaces.

**SwiftUI view tree (rendered inside the panel):**
- `UsageDetailCard` — **the window's name has the row to itself; what is spent and when it resets pair off on the line below the bar.** They used to share the top line, which is fine for "5-hour limit" and falls apart the moment a limit is scoped to a model group: "5-hour limit · Claude and GPT" beside "Resets 9月6日 18:14" does not fit a 250pt card, and the half that got cut was the name — the half that says which limit this is. All of Antigravity's four windows are scoped, so it went from an edge case to the normal one.
- `UsageBubbleShape` — the details card's body *and* its pointer, drawn as **one path**. The two are separate subpaths filled together, so they must **wind the same way**: under the non-zero fill rule opposite windings cancel where they overlap. Mirroring the geometry for the left edge reversed the tail's direction and punched a visible gap between tail and card, so the tail's traversal is flipped to match (`sweep`). Any change to this shape needs checking on both edges. They used to be two views in a stack, with the pointer nudged into place by padding; switching providers changes the card's height and the pointer's target at once, and two views animating separately drift apart — the tail visibly detaches mid-transition. Keep them one shape. `pointerCenterY` is the shape's `animatableData` so the tail moves as geometry rather than as its own animation.
- `FloatingUsagePanelView` → `UsageDockView` (the always-visible rail of per-provider rings) with `UsageDetailCard` (the flyout for the selected provider) hung off it as an **overlay**, not as a sibling in a stack. Selection is **hover-driven**: pointing at a ring opens that provider's card, and the pointer leaving the panel closes it. Opening and closing come from different mechanisms on purpose — see `PointerEntryReporter` / `PanelPointerWatcher` below.
  **The panel window never changes size** (`FloatingPanelController.Layout.width` is fixed at card + pointer + gap + rail), and the card is an overlay rather than a stack child, for the same reason in both cases: anything that changes the geometry the rail is laid out in will animate the rail sideways when the card opens, even though the rail's position on screen never actually changes. Two separate versions of that bug were fixed by removing the movement rather than trying to animate around it. Keep it that way: don't resize the panel, and don't put the card and the rail in a shared stack.
  **The rail's vertical offset (`.padding(.top, railTop)`) must be applied *after* the card's overlay, never before.** The card is aligned to the top of whatever it is an overlay on, and its own padding is measured from the rail's top — so padding first anchors it to the top of the *panel* instead, drawing every card `railTop` too high and slicing it flat against the window's edge. That shipped once, and it is invisible until the rail is somewhere other than the middle.
  Because the frame is fixed, **it has to be tall enough for the tallest card, not just the rail** — `Layout.height` takes the larger of `DockLayout.maximumHeight` and `DetailCardLayout.maximumHeight`. A card taller than the window gets sliced off flat against its edge, which reads as a drawing bug rather than as a card that didn't fit; that is exactly what happened once Codex began reporting a third limit. The rail is therefore centred vertically in the panel (`PanelEdge.railAlignment`), and `FloatingUsagePanelView.railTop` is the offset that anything measured from the rail needs before it can be compared against the panel. Card positions stay rail-relative and may go negative; the pointer's position is panel-relative.
- `PointerEntryReporter` / `PanelPointerWatcher` — the two halves of the hover behavior, both `NSViewRepresentable`, both attached as `.background`. **SwiftUI's `.onHover` will not work here**: it tracks only while the app is active, and Pulse is an `.accessory` app behind a non-activating panel that never becomes key, so it is essentially never active. `PointerEntryReporter` uses an `.activeAlways` `NSTrackingArea` and reports **only entering** a ring. `PanelPointerWatcher` samples `NSEvent.mouseLocation` on a timer and reports it as a point, which `FloatingUsagePanelView.isOverContent` tests against the rail and the card — *not* against the window's frame, since the panel is kept at full size and is mostly transparent, so "inside the window" would hold the card open across a wide empty area.
- **The ends lose the flare's worth of padding when the rail floats** (`DockLayout.endPadding(docked:)`). `verticalPadding` is measured from the panel's edge, not from the body's flat start, because docked the concave flare carves `flareHeight` out of each end — so the black actually visible above the first ring is the difference, 22pt against a 30pt gap between rings, which reads as deliberate. Off the edge there is no flare and the whole 46pt shows, which reads as the ends having been forgotten. Taking the flare off the number keeps the *visible* breathing room identical in both states, which is the thing anyone is actually looking at. The rail is 48pt shorter floating; the window is not, being measured docked, so nothing resizes as the rail comes off an edge. **Anything measuring the rail has to be told which state it is in** — the ring centres and `PanelHitArea.account` included, or a click lands beside the ring it appears to be on.
- **The rail hides down to a 6pt sliver at the screen edge** when the pointer is elsewhere (`AppSettings.autoCollapse`, on by default) — but **only while docked**. Off the edge it stays open: hiding earns its keep against the side of the screen, where the rail is over whatever is behind it and getting it back is a flick at an edge that cannot be missed, but a pill in the middle of the desktop is neither out of the way nor easy to find again. So the sliver is always hard against a screen edge, and `PanelHitArea.strip` can assume it.
  **The sliver is not a separate view.** It is `DockBerthShape` with `openness` at 0 — the flare wound down to nothing and the corner radius equal to the whole width, which degenerates into exactly the rounded-on-one-side sliver. `openness` is the shape's `animatableData`, so the outline is redrawn at every step and the rail visibly *grows* out of the sliver, instead of one view fading out while another fades in. Two views swapped by a transition is what this used to be, and it read as exactly that. The rings fade on their own slightly later curve (delayed on open, quicker on close) so the berth opens *then* fills, rather than contents appearing over a shape that is still a sliver. Measured while opening: 6 → 38 → 57 → 63 → 64pt, never backwards, rings arriving at 63.
  The view is laid out at the rail's full size whatever it is drawing, so collapsing changes *nothing* about the geometry the card is positioned in — the same reason the panel never resizes. The rings keep their tracking areas only while expanded (`isInteractive`): an invisible ring with a live tracking area opens a card for a provider nobody can see.
  **Two things have to be true for the capsule to be draggable, and they are in different files.** First, something in the panel must *claim* the point, or the window is never handed the press at all — that is `PanelSurface`, which is hit-testable on purpose and carries a `contentShape` of the capsule's own outline. Marking it `allowsHitTesting(false)` (which it was, from the day the Liquid Glass option arrived) is what killed dragging in the empty black between the rings: the rings claim their own area for their tracking areas and went on working, the gaps claimed nothing and went dead. Second, the press has to be *taken*, and that is the window:
  **Dragging belongs to the window, not to a view inside it** (`FloatingPanel.sendEvent` in [FloatingPanelController.swift](Sources/Pulse/FloatingPanelController.swift)). It was an `NSViewRepresentable` in the SwiftUI tree for a long time, and that is the wrong place for it: a press only reaches a view inside `NSHostingView` if SwiftUI claims the point first. Once the berth became a `PanelSurface` — added for the Liquid Glass option, and marked `allowsHitTesting(false)` so it could never take a press away from the handle — nothing claimed the empty black between the rings, and the panel could be dragged by its rings and nowhere else. The rings work because their tracking areas carry a `contentShape`; the gaps had nothing. Laying a shape *over* the handle to claim those points was worse: it swallowed the press rather than passing it down, and then nothing could be dragged at all. `sendEvent` sees every event the window server hands the window, before any of SwiftUI's hit testing and before whatever Liquid Glass installs for itself.
  The window is handed **two** rects, not one: `grabArea` (the rail, or its sliver when collapsed) decides whether a press is taken, and `railFrame` (always the rail) is what the placement arithmetic runs on. Collapsed, what is grabbed is the sliver but what is *placed* is still the rail — handing the placement a 20pt sliver where it expects a 64pt rail throws the panel across the screen on the first drag. Both are sized to what is actually drawn, or a press anywhere in the transparent band would move the panel instead of passing through to whatever is behind it.
  **A ring click and a ring drag share that same window-level input path.** `FloatingPanel` records the press, marks it as a drag only after a real `leftMouseDragged`, and reports a click on mouse-up otherwise. `PanelHitArea.provider(at:...)` accepts only the visible circle, so labels and berth gaps remain drag-only. The click starts a provider-scoped refresh, and `UsageStore.isRefreshing(_:)` is what the ring shows it with: the usage arc **dims but does not move**, and a short bright segment of the ring travels round over track and arc alike. Rotating the usage arc itself was the first attempt and it ties the feedback to the number being shown — at 0% there is no arc, so a click produced no visible response at all (measured: nothing, for the whole 650ms), and at 95% a rotated arc is nearly indistinguishable from a still one. It also takes the reading away while it spins, since the arc starting at twelve o'clock is what makes it a gauge, and puts it back with a jump when the spin stops at whatever angle it had reached. The travelling mark is the usage colour, not white: white on these rings is spoken for by the CLI-activity mark, which rides the empty circle further in. The refresh is held for a minimum 650ms so a local read that returns within a frame still registers, and the arc and the figure both animate to their new values — a manual refresh exists to show what moved. Keep the physical click here rather than adding a SwiftUI button gesture: `sendEvent` deliberately takes the press before SwiftUI sees it. The ring still exposes a default accessibility action through SwiftUI.
  **`hitTest` is worthless for this.** It reported the old handle as reachable at every point of the rail including the gaps, and at widths it did not have (the full 64pt while collapsed to 20). Both are impossible. It lied about Liquid Glass the same way. What a probe *can* answer is geometry — is this point inside the grab area — and that is worth checking, since a missing `railFrame` closure made every press refuse silently. Whether a real click arrives at all is only answered by a person pressing it: ask, rather than building a fourth probe that agrees with the first three.
  The sliver **must be reachable without leaving the rail's hit area** — `PanelHitArea.stripIsContainedInRail()` asserts it, over every edge and every rail length up to `PanelMetrics.railCapacity`, against the metrics actually in force. It is run from `FloatingPanelController.init`, which is the point those metrics are settled; it went uncalled for a while, and the doc comment beside it named a `PanelHitAreaCheck` that has never existed. Its bound was `Provider.allCases.count`, which stopped describing the rail the moment the rail was keyed by account. Hiding happens only when the pointer is outside the *rail*; if the sliver poked out beyond it, leaving the rail would land on the sliver, whose tracking area shows it again, which hides it again. That is the same open/close loop below, in a new costume.
  The sliver takes the usage colour once a limit is past the warning threshold. A monitor that hides itself has to keep one way of saying "look at me", or auto-hide quietly switches off the thing the app is for.
  **The sliver's tracking area cannot be the only way `isHovered` gets set.** While the panel is floating there *is* no sliver, so dragging a floating panel onto a screen edge docked it with `isHovered` still false and it snapped shut in the hand holding it. `pointerMoved` sets it too, from the same test that decides when to hide — which is precisely why that cannot restart the loop below: the two can never disagree about whether the pointer is on the panel.
  **Do not reintroduce exit events as the close trigger.** Views appearing, moving and animating under a stationary pointer fire spurious exits; closing on one puts the pointer back on a ring, which reopens the card, which loops forever. Splitting it this way — enter from tracking areas, leave from sampling the real pointer position — makes that loop structurally impossible.
- `PanelPlacement` — two ways in, and they must not fight. `update(dock:...)` changes the placement **and asks for the window to be moved** (`onChange`, which `FloatingPanelController` wires to `placePanel`); `record(...)` only stores it, and is what the drag uses because the window has already moved itself as the pointer went. Picking a position in Settings went through the storing path once, so the content mirrored while the window stayed put and the rail ended up stranded mid-screen.
  **The panel can be dragged anywhere on the desktop**, and fuses to a screen side once the rail comes within `PanelPlacement.dockDistance` of it. Docking is decided *during* the drag, not on release — a snap that waited for mouse-up would jump the panel out from under the pointer. Floating positions are clamped to stay at least that far from both sides, so "floating" can never mean "touching but drawn as if it isn't".
  **The panel goes on any display, and remembers which** ([PanelScreen.swift](Sources/Pulse/PanelScreen.swift)). The drag clamps the rail to the usable area every frame, and that was measured against *the window's own screen* — so a drag towards a second monitor was put back where it came from on every frame and nothing ever crossed. It is the screen under the **pointer** now. The two stored ratios are fractions of one screen's usable area, so they say where on a display the rail sits and nothing about which, and without a stored display the panel came home to whichever screen was main at every launch and every settings change. What is stored is the display's **UUID**, not its `CGDirectDisplayID` — that one is handed out afresh at every reconnection, so it is not an identity. A stored display that isn't attached resolves to nil and the caller falls back to main, and `didChangeScreenParametersNotification` re-places the panel so unplugging a monitor cannot strand it in a space nobody can see (not during a drag, which is already moving the window itself).
  **The stored position is the rail's, never the window's.** The window is far wider than the rail (it carries the space the card unfolds into) and which side of it the rail sits on flips at the middle of the screen; storing the window's position would throw the rail a card's width sideways at that moment — while the user is holding it.
  `PanelPlacement.layout(in:panel:rail:)` is the **single source of truth** for the geometry, returning the window's frame *and* the rail's offset inside it — `railTop` down a side, `railLeading` along the top. They trade off: the window is kept inside the visible area so the card always has room, and whatever that clamping cost is comes back as the rail's offset inside the panel, so the rail itself lands where the user put it. Without that offset the rail would stop a couple of hundred points short of the top and bottom of the screen. The drag handle and `placePanel` both go through it rather than doing the arithmetic twice.
  Because `railTop` depends on the rail's height, **anything that changes which providers are shown has to re-place the panel** — `FloatingPanelController.settingsChanged()` does.
  **The rail also lies along the top of the screen**, and that is an *axis*, not a third special case (`PanelEdge.axis`). Everything that used to branch on left-or-right — which stack the rings sit in, which end the flare fuses into, which way the card unfolds, which of the two stored ratios is pinned, where the sliver goes — actually only cares about the axis, so a fourth edge would be an entry in a few switches rather than a rewrite. Both shapes are drawn **once, facing right, and transformed**: mirrored for the left edge, turned a quarter for the top. A rotation is used rather than a reflection deliberately — it preserves winding, and `UsageBubbleShape`'s body and tail have to wind the same way or they cancel where they overlap.
  **A top-docked rail goes to the display's *physical* edge, above the menu bar** — `FloatingPanel.topEdge(of:)` and `applyLevel(for:)`. `visibleFrame.maxY` is under the menu bar, and a rail parked a menu bar's height below the top of the screen is not against the top of the screen and looks it. Reaching the edge takes two things together: the placement has to aim at `frame.maxY`, **and** the window has to be at `.statusBar` level — `.floating` is *below* the menu bar's own level, so a panel placed at the edge is simply drawn over by it. The level goes back to `.floating` off the top edge, so the panel never sits over the menu bar for nothing. A notch stops it (`safeAreaInsets.top`), and stops it for a reason worth writing down: there *is* screen either side of a notch — that is where the menu bar is drawn — but the rail is far wider than either strip. Measured against a 14", a 16" and an M-series Air: centred, even a three-provider rail at 260pt straddles the notch, and a full six at 458pt covers it entirely. So on a notched Mac the rail stops at the notch's own line, which is also where the menu bar ends, and hangs from it. The lower of `frame.maxY - safeAreaInsets.top` and `visibleFrame.maxY` is taken rather than trusting the two to be equal — only one of them is the notch's, and the rail must never be asked to draw into a row it cannot be seen in. Measured on a 2560×1440 display with a 30pt menu bar: the rail's top edge lands at 1440.0.
  **The panel window *does* resize, but only when the rail is re-docked onto the other axis** (`FloatingPanelController.Layout.size(for:)`). That is not a contradiction of the rule above: what must never resize is the window *while a card opens*, because that moves the coordinate space the rail is laid out in mid-animation. Re-docking happens under the pointer with no card open.
  **Docking to the top is tested against the pointer, not the rail.** A rail standing on its end is most of the screen tall, so its top edge reaches the top of the display almost as soon as it is lifted — testing that flips it on its side the moment it is picked up. Throwing the pointer at the top of the screen is the deliberate gesture. And because the rail *turns* as it crosses onto the other axis, everything after the dock is decided is measured in the orientation it is about to be in, and the grab offset is dropped in favour of centring it under the pointer: carrying a grab offset across a quarter turn puts the rail somewhere the hand holding it never asked for.
  **A turn is a change of axis, and must never be inferred from the rail's size.** It was — `landingRail != rail` — and that was right until the ends began losing the flare's padding off an edge, which makes the *same* rail 48pt shorter floating. From then on every dock↔float transition on one axis counted as a turn: the rail re-centred itself under the pointer for one frame and snapped back 276pt on the next, twice per drag. The size does still change there, so the grab is re-measured to hold the rail's **centre** rather than its offset — half the 48 comes off each end, so the rings then do not move at all (measured: ring centre 332.0pt, unchanged across the transition; it moved 252 and then 276 before).
  **A floating landing works out its own side rather than reading `placement.edge`.** That property is a frame behind during a drag — `record` runs later in the same pass — so on the frame a *top*-docked rail is lifted off it still answers `.top`, which sized the window for the horizontal axis while the content had already redrawn as a vertical rail: 52pt of it sliced off, and the hit rect 116pt from where the rail was actually drawn.
  **Both rails can drop their percent labels, with opposite defaults** (`AppSettings.sideRailShowsPercentages`, on; `topRailShowsPercentages`, off). Against a side of the screen the label sits under its ring and costs nothing; along the top it is a second line of type directly under the menu bar, which turns a compact pill into a banner. Measured at standard scale, six providers: 458×64 without the labels, 458×77 with. Down a side the label costs only length, and dropping it shortens a six-ring rail from 584 to 458pt at standard scale — the **width stays at `DockLayout.width` either way**, because the flare and the corners share that measurement (`cornerRadius + flareWidth <= width`) and narrowing it would fold the berth in on itself. Both flags live on `PanelMetrics` beside `scale` and for the same reason — they change what the AppKit frame is worked out from before SwiftUI lays anything out — and both have to be in `FloatingUsagePanelView`'s `.id(...)` or the rings are drawn at one size in a berth built for the other.
  **Docking left mirrors the whole panel**, and floating changes the silhouette: `PanelEdge` supplies the alignments and the card's offset direction, and `DockBerthShape` draws either the edge-fused flare or, off the edge, a true capsule with **circular** half-round ends — an edge-hugging shape in the middle of the desktop reads as a rendering fault. The ends are the one place the squircle used everywhere else is wrong: a squircle eases its curvature into the straight edge beside it, and at the rail's width the two corners of an end meet with no straight edge between them, so there is nothing to ease into and it comes out a flattened lozenge. `DetailPointer` and the docked berth draw facing right and flip the finished path. Anything visually asymmetric added later has to handle both edges *and* both dock states.
- **A white arc turns inside the ring while that provider's CLI is working** ([AgentActivity.swift](Sources/Pulse/AgentActivity.swift)), polled every 2s on its own clock — a turn starts and finishes in seconds while usage moves in percent, so the two cannot share a schedule.
  **"Working" is not "written to recently."** That was the first attempt and it is wrong in both directions at once, with no value of the timeout that fixes it: a turn running a slow tool writes nothing for minutes, so a short window stops the spinner mid-turn, and a finished turn goes on spinning for the rest of a long one. Both CLIs state the answer outright, so only the **tail** of each live transcript is read (a 20MB file costs a few kilobytes to consult) and the last decisive record settles it:
  - Claude Code stamps each assistant record with `stop_reason` — `tool_use` means it is handing off to a tool and will be back, anything else ends the turn. A trailing `user` record (a prompt, or a tool result coming back) means it is the model's move. Everything else in the file — `queue-operation`, `attachment`, `custom-title`, `mode`, `system` — is bookkeeping and must be skipped, not treated as activity.
  - **Except the one that says the turn was interrupted.** Escape leaves a `user` record reading `[Request interrupted by user]`, and taken as an ordinary prompt it means the opposite of what happened, so the ring turned for the whole grace period after every interrupt. It ends the turn.
  - **An assistant record with no `stop_reason` at all is a subagent's**, not a turn mid-stream. Measured over this machine's transcripts: 159 of 160 are `isSidechain`, and one of them is the file's last word whenever a background agent outlives the turn that started it. It counts as working, but on the short grace below.
  - Codex brackets each turn with `task_started` / `task_complete`, and `turn_aborted` when it is stopped. Its `*_call` / `*_call_output` pairs (`function_`, `custom_tool_`, `tool_search_`) say **which half** of a turn is in flight, which is the only way to tell — a turn is bounded by `task_started` alone until it completes.
  **What a turn is waiting for decides how long its claim may outlive its last word** (`AgentActivity.Wait`). One timeout cannot serve both, and the single 5-minute one did not: it has to be long enough for the slowest tool, and that is far longer than a dead session should go on spinning. Measured here over 3,110 turns and 2,783 tool calls — waiting for **the model** is a median 7s and 99% inside 70s (grace 90s), waiting for **a tool** is a median 2s but writes nothing for as long as a build takes, 15 minutes at the extreme (grace 5 min, which is what the old single timeout was sized for).
  **The grace runs from the record's own timestamp, not the file's modification date.** Claude Code goes on writing bookkeeping into a transcript long after the turn ended — titles, modes, background monitors — so the file's date says when something last *touched* it, not when the agent last *did* anything. Timed off the file, a session that died mid-turn stayed "fresh" for as long as anything kept poking it, and the ring turned indefinitely. Both CLIs stamp every record that means anything; the bookkeeping ones carry no stamp, which is part of what marks them out.
  An unrecognised tail still falls back to "written to in the last 30s" so a format change degrades instead of breaking. All live transcripts are consulted, not just the newest — two terminals can be running at once.
  `AgentActivity.verdict(for:provider:)` is internal on purpose: the rule is the whole feature and it is checked against synthetic *and* real transcripts cut at genuine turn boundaries. The monitor is stopped whenever the panel is hidden or the display is asleep, and the refresh loop reads its answer instead of scanning a second time.
  The arc rides the **empty ring between the icon's disc and the usage ring**, never on the ring itself — colour on that circle means how much of the limit is gone, and a white arc laid over it would cover the answer. It is driven by Core Animation rather than a per-frame `TimelineView`: Pulse is an `.accessory` app behind a panel that never becomes key, so a schedule tied to the app's own frames is a poor bet. The `spinning` flag must be reset on disappear or a second appearance animates nothing.
- **The pointed-at halo hangs on the progress arc, not on the ring view, and its inward half is masked away rather than covered up.** A `.shadow` on a composed view is drawn behind *everything* in it — including behind the icon, whose antialiased edges let it through, so the mark picks up a wash of whatever colour the limit currently is (measured: a green cast of +16 over neutral on a 35% ring, against +0.0 unhovered). Moving it onto the arc fixes which layer it is on but not which direction it spreads, so the ring's centre clearing is cut out of the halo's own layer; only the outward half — the part that was wanted — survives. The arc itself sits well outside that hole and is untouched.
  It used to be an **opaque disc** laid over the blur instead, which is invisible on the black panel because it is black on black. There is no such colour on Liquid Glass: the disc had to follow whatever appearance the material picked, and over a bright backdrop that is a solid white coin behind the mark — which is exactly what it looked like. Measured over a checkerboard: the clearing read 213/205/212 with the disc, taking nothing from the pink and purple behind it, and 193/128/181 with the mask. A mask has no colour to get wrong, so the same code now serves both surfaces; the black panel renders byte-for-byte as before.
- **Liquid Glass is an option, off by default** ([PanelSurface.swift](Sources/Pulse/PanelSurface.swift), `AppSettings.usesGlass`). Black stays the default because the panel sits over the user's work all day and a solid surface is legible over anything; glass takes on whatever is behind it.
  **Do not scrim the glass, and do not take the surface out of hit testing.** It was marked `allowsHitTesting(false)` here for a long time and that is what stopped the panel being dragged anywhere but by its rings — see the drag note above. Nothing is at risk in claiming those presses: the window takes the drag before any view sees the event.
  **Do not scrim the glass.** Darkening it by hand was the first attempt and it fights the material — Apple's guidance is that Liquid Glass manages its own legibility, shifting tint and dynamic range and switching between light and dark to suit its backdrop, and `Glass.tint` applies a hue rather than a darkening (measured: a black tint barely moved the surface luminance). What makes content readable on it is letting the content adapt too, which is why everything drawn on the panel uses `.primary` rather than a hardcoded white, and why the dark appearance is pinned **only** when glass is off.
  That pin goes through `.environment(\.colorScheme, .dark)`, not `preferredColorScheme` — the latter is a window-wide preference and cannot express "this subtree is dark".
  **Known cost, and why the toggle carries a note.** On macOS 26 the material implements its own interactivity *outside* SwiftUI's hit-testing chain and swallows real mouse input across its whole area, so with glass on the panel can only be dragged by its rings — ordinary views drawn outside the effect. `.allowsHitTesting(false)`, `.disabled(true)` (the workaround the forums suggest), and opaque ink both above and below the material were all tried; none help. See developer.apple.com/forums/thread/816366.
  **Suspect this was never a glass bug.** The reported symptom — "only the rings can be dragged" — is exactly what the SwiftUI-hosted handle produced on the *black* panel too, once the berth stopped claiming presses. Now that the window takes its own events the material has no say in it. If dragging works on glass, this whole note and the settings caption that goes with it should come out.
  **This cannot be reproduced in a harness**, which is what made it expensive to find: `hitTest` and synthesised `NSEvent`s both report the drag handle as perfectly reachable, because they bypass whatever the material installs. Only real input is affected. When a symptom survives every local probe, search for it before theorising further — the answer here was a filed system bug, not our code.
  **Use `Glass.clear`, not `.regular`.** Measured five variants in a transparent panel over a bright, busy backdrop: SwiftUI's `.regular` comes out an opaque milky white with nothing showing through — frosted glass, not Liquid Glass — and `NSVisualEffectView` is worse. `.clear` and AppKit's `NSGlassEffectView` both keep the content behind visible. All five *do* sample behind the window, so a transparent `NSPanel` is not the problem; the variant is.
  The material needs macOS 26; the package deploys to 14, so there is an `#available` guard with a vibrant blur behind it.
- `UsageRingView` / `LobeIconView` — shared progress-ring + provider-icon component. `LobeIconView` renders its mark as a **template image with no colour of its own**, so it inherits the ambient foreground style: white where callers tint it against the panel's black, and the ordinary label colour in the settings sidebar. Don't reintroduce a hardcoded colour there.
- **SwiftUI drop-downs can't be given a width on macOS.** `Picker` and `Menu` both size to their longest option; `.frame(width:)`, `min`/`max` widths, `fixedSize`, and a fixed-width custom label were each measured and none of them move either control. So settings drop-downs vary in width, right-aligned at `SettingsLayout.controlWidth` as a *ceiling* — long labels truncate rather than towering over their neighbours.
  Wrapping `NSPopUpButton` in an `NSViewRepresentable` does give a true fixed width (it is laid out by SwiftUI's frame), and that was built and then removed: uniform 180pt boxes left short labels like "Automatic" floating in mostly empty controls, which looked worse than the ragged column it fixed. Pickers sized to content is also what macOS itself does. Don't rebuild it without checking that first.
- **Settings subtitles are one line.** A caption under a control is read at a glance or not at all, and a three-line explanation of a toggle turns the pane into a document. Say what the control does and stop; the reasoning behind a default belongs in this file, not on screen. The exceptions are the two places where the text *is* the feature — the money card's provenance note and the estimate's caption, which exist to stop a reader taking an inferred figure for a reported one.
  Note a joined sentence needs no space after a Chinese full stop: `。` is full-width and carries its own, so `glassSubtitle` adds a separator only when the first half doesn't end in one.
- `SettingsView` / `SettingsRow` — the settings window: a `NavigationSplitView` source list beside panes built from `SettingsGroup` (a captioned rounded card) and `SettingsRow` (title + optional subtitle on the left, control on the right). `SettingsPane` carries the selection, including one case per provider (`.provider(_:)`), so each provider gets its own pane in the sidebar's Providers section. Note that `ImageRenderer` cannot draw `NavigationSplitView` or AppKit-backed controls, so offscreen renders of this window come out as placeholders — check it by running the app.
  **A provider with one route has that route *named*, and the name belongs to the provider** (`Provider.soleRoute`). It was a ternary here — Cursor's wording, or else Antigravity's — so the first single-route provider added after those two inherited Antigravity's sentence: Grok's pane read "Antigravity's language server · Only while Antigravity is open", about a route it does not have and an app it has nothing to do with. It was not a wrong string but a missing branch, and it read as perfectly deliberate copy, which is why nothing caught it before a screenshot did. The switch is on `Provider` and exhaustive, so the next one added cannot quietly take somebody else's words; the row is simply not drawn when the answer is nil.

**Settings and state:**
- **A second, thinner arc can say how far through the window the clock is** (`AppSettings.showsWindowClock`, off by default; `UsageWindow.elapsedFraction(at:)`). Asked for by a user, and it answers the question the percentage alone cannot: 80% spent a fifth of the way into a window means running out, 80% spent with minutes left means it was budgeted about right. Three rules make it fit. It goes **outside** the usage ring, because the circle inside is spoken for — the CLI-activity mark rides there. It is a **neutral at low opacity, not a second hue**: colour on these rings already means one thing, a second colour would be a second language to learn, and a fixed hue would clash with a colour someone chose for the ring; a hairline at a different radius reads as a different measurement without claiming a status. And it is an **overlay applied after `.frame(width: diameter…)`, never a child of the ZStack** — a fixed-size child sets a stack's size, and this circle is deliberately wider than the ring, so inside the stack it grew the usage ring itself from 36pt to 52pt (measured), which moves every ring centre the hit testing is checked against. As an overlay it changes nothing: ring reports 36pt either way, rail sizes identical, 168 ring clicks still land right, and the circle clears the rail's width at all three sizes (6.6 / 8.0 / 9.8pt of margin). It is worked out from `resetsAt` and `windowSeconds`, so it is **nil rather than guessed** when a provider gives one without the other — and it moves on its own clock, so a 60-second ticker drives it rather than the usage loop, which backs off to half an hour.
- **The figure can sit above the ring instead of below it** (`AppSettings.labelAboveRing`, off by default). Below is the default because the ring is what the rail is for and reads first, with the number confirming it underneath. The swap changes nothing about the rail's size — measured both ways, side 64×584 and top 458×64 — but it does move **where a ring sits inside its item**, and the drawing and the hit testing work that out separately. `DockLayout.ringOffsetInItem(on:)` is the one number both go through: `firstRingAlong` adds it down a side, `ringCentreAcross` across the top, since only the rail's own axis stacks the two. Get that wrong and a click lands on the number instead of the ring above it. Checked at every edge, both dock states and 1–7 accounts: 168 rings, drawn centre against hit-tested centre, worst disagreement 0.0000pt. It rides on `PanelMetrics` like the other rail metrics and needs the same `.id(...)` entry.
- **The layout constants are budgets, and a short budget is a squeeze, not an approximation.** The AppKit frame is worked out from `DockLayout` before SwiftUI lays anything out, and the hit testing steps along the rail in those same units — so anything that renders *larger* than its constant overflows, and anything that renders *smaller* leaves slack. Both were happening. `percentTextHeight` was 15 against a line that renders at 15.6–16.0 per unit of scale, and the overflow, centred, drifted the ring centres up to 6pt from where the hit testing looked. `itemLength(on: .horizontal)` was the ring's diameter on the stated premise that the label is narrower — measured, "100%" is *wider* at every size (by 1.5/1.0/1.1pt), so a top rail was built a point short per ring and every label rendered as "10…". Both constants are now measured with the real font and rounded **up**, and **every item is pinned to its budgeted length** (`.frame` on the item, along the rail's axis) so a font that renders narrower cannot accumulate either: without that, eleven rings drifted 12.6pt. Verified over the whole matrix — three edges, docked and floating, 1/2/6/11 accounts, three sizes, three spacings, both percentage flags, label above and below: 8,640 rings, worst disagreement **0.72pt**, and it no longer accumulates.
  Note `firstRingAlong` differs by axis for the same reason: down a side the ring sits `ringOffsetInItem` into the item, but across the top it is *centred* in the item's width, which stopped being half a ring the moment the item became as wide as the label.
- **The gap between rings is its own setting** (`RailSpacing`, tight/standard/loose at 0.6/1/1.4). Deliberately *not* folded into `PanelSize`: that scales everything at once, and wanting seven rings to take less room is a different wish from wanting bigger rings. It touches `DockLayout.itemSpacing` and nothing else, so the rings and the rail's width are identical at all three — measured with seven accounts: 599 / 671 / 743pt long, 64pt wide throughout. It rides on `PanelMetrics` for the same reason `scale` does, and needs the same `.id(...)` entry.
- **The whole panel scales from one multiplier** (`PanelSize` small/standard/large, `PanelMetrics.scale`). Every measurement in `DockLayout` and `DetailCardLayout` is a computed `static var` reading it, which is what keeps the AppKit window frame and the SwiftUI content in step — the frame is worked out from those constants before SwiftUI has laid anything out, so a size that only one side knew about would tear them apart. Measured: rail 52/64/78pt wide, window 280/342/417pt, and `PanelHitArea.stripIsContainedInRail()` holds at all three, on every edge.
  **The card's type scales with them, and once did not.** Its *width* followed `PanelMetrics` while every font inside it was written as a constant, so at Small a 205pt card still tried to hold 14pt text and truncated its own title and reset times, and at Large a 305pt card held the same 11.5pt rows and read as half empty beside rings that had grown. The line-height budgets in `DetailCardLayout` were already scaled, which is what makes the ratios hold once the fonts are too. Anything new drawn on the panel takes its size from `PanelMetrics`, never from a literal.
  **Anything derived from `PanelMetrics` must be a computed `var`, never a `static let`.** A `static let` is worked out once per process and never again, so `FloatingUsagePanelView.cardInset` kept whichever size was current when it was first read — switch to Large afterwards and the card was offset by the old width, 61pt short against a 78pt rail, which parks it squarely on top of the rings. Rebuilding the view does not help; nothing rebuilds a `static let`.
  The constants are plain statics, so SwiftUI cannot observe them: `FloatingUsagePanelView` carries the size in its `.id(...)` alongside the language, for the same reason.
- [LoginItem.swift](Sources/Pulse/LoginItem.swift) — opening at login, on by default. Two routes, for the same reason the usage services have two: `SMAppService.mainApp` is the supported API and the one System Settings lists, but it only works from a real `.app` bundle — run as `swift run Pulse` it reports `notFound` and cannot register (measured). So without a bundle a launch agent is written to `~/Library/LaunchAgents` instead; launchd reads that folder at login, so nothing needs loading. No `KeepAlive`: quitting Pulse should leave it quit until the next login.
  **"On by default" is a decision taken once**, recorded by its own flag — switching it off, here or in System Settings, has to stick, so this must never re-enable on a later launch. And because rebuilding moves the executable, `repairPathIfNeeded` rewrites a stale agent, exactly as `StatusLineHook` does for the same reason.
  The toggle reads the *system's* state rather than a stored preference, so it can't drift from what macOS actually has.
- [AppSettings.swift](Sources/Pulse/AppSettings.swift) — `@Observable`, persisted in `UserDefaults`: whether the panel is shown, and which providers appear in the rail (never empty — the last one can't be switched off, or there would be nothing to hover and nothing to grab to drag the panel). **What must not be empty is the rail, not the provider set**: an added account is switched on through its own list and is not a provider, so someone monitoring a second Codex login and nothing else has an empty provider set and a perfectly full rail. Rebuilding from `allCases` there switched all seven back on *and wrote it to disk*, destroying the choice rather than merely misdrawing it. Its `onChange` closure is how the AppKit side hears about changes.
- Turning a provider off shortens the rail (`DockLayout.height(for:)`), but **the panel window stays at `DockLayout.maximumHeight`** so nothing has to resize; the rail simply draws shorter and the rest of the panel is transparent. Anything measuring the rail must use `FloatingUsagePanelView.railHeight`, not the window's height.

**Usage data — reported by the provider, with one labelled exception:**
- [UsageProvider.swift](Sources/Pulse/UsageProvider.swift) — the `Provider` enum (`.claudeCode`, `.codex`, `.antigravity`): display name, icon resource, and the two things that differ per provider rather than per feature. `keepsLocalTranscripts` is false for Antigravity, which is an editor rather than a CLI and leaves no session files — so the spending history, the estimated value of a window and the "working right now" mark are **left out** for it rather than shown as zeroes, which would read as "you have spent nothing". `hasSourceChoice` is false for the same reason its route is single.
- **A first run starts with what is installed**, not with everything (`Provider.installedOnThisMac`). Two things make this safe and both were got wrong first:
  **"Has Pulse run here before" cannot be read off the enabled set.** 1.0.0 computed that set and never wrote it — assigning a stored property in `init` does not run its `didSet` — so it is absent for everyone upgrading, and an upgrade looked exactly like a first run. `Key.offeredProviders`, which 1.0.0 *did* write, is the evidence instead; `Key.hasRun` takes over from the next launch. Get this wrong and an upgrade silently rebuilds the rail from what happens to be installed, dropping providers it cannot see.
  **The offer-once union has to run before the offered list is stamped.** Stamping first marks a brand-new provider as offered without ever enabling it, which puts it out of reach of the rule that exists for it — permanently invisible.
  The computed set is written back, and can never be empty: a stored list whose names no longer parse falls back to everything rather than to a rail with nothing to hover. Showing four rings to someone who uses one is three quarters of a rail greyed out — which reads as broken rather than as not-yet-configured — and a rail half again as tall as it needs to be. Only the presence of `~/.claude`, `~/.codex` and `/Applications/Antigravity.app` is checked, never their contents; OpenCode Go stays off because it cannot work without a key. If nothing at all is found, everything is shown: an empty rail has nothing to hover and nothing to grab.
- **A provider with nothing fetched yet does not claim to be loading** (`UsageStore.initialState(for:)`). Every account used to be seeded `.loading`, and for one that needs a credential Pulse hasn't got that never resolves — nothing is queued for it, and while it is switched off nothing ever will be. Its own settings pane sat reading "Reading…" indefinitely, which is untrue *and* the opposite of the one instruction that would help. It is seeded with the reason instead, and `loadAPIKeys` rewrites that when a key is entered or cleared — only over a placeholder, never over a reading actually taken.
- **Each provider's pane has its own refresh**, above its limits, with the time of the last reading beside it. The rail does the same on a ring click, but nobody reading a settings pane should have to go and find that.
- **The rail's order is the user's** (`AppSettings.providerOrder`, resolved through `orderedProviders`). The stored list is never trusted as written: a provider added in a later version is missing from every list saved before it existed, and one removed would still be named in lists saved while it did — so unknown names are dropped and unmentioned providers are appended in declaration order, which puts a new one at the bottom of the rail rather than in the middle of it. The settings sidebar follows the same order, since a sidebar that disagrees with the thing it configures is its own small confusion.
  **A click has to be matched against the displayed order too.** `PanelHitArea.provider` maps a position to an index, so `FloatingPanelController` hands it `orderedProviders.filter(isEnabled)`; passing `Provider.allCases` refreshed whichever provider used to occupy that spot. And `providerOrder` deliberately does **not** call `onChange` — that is how the usage loop hears about settings and it refetches everything, which no rearrangement should cost anyone.
  Arrows, not dragging: four rows is not enough to make a drag worth learning, and a drag that misses does something whereas an arrow that misses does nothing.
- A provider added later is **switched on once, the first time it is seen** (`AppSettings.restored`, `Key.offeredProviders`) — **but only if it can report something without being set up** (`Provider.canReportWithoutSetup`). One that needs a key Pulse hasn't got would take a place on the rail to say "enter an API key in Settings" about a service the person may not have an account with, and with fourteen providers that is most of the rail. It is still stamped as offered, so this stays a decision taken once: it appears when it is switched on in Settings, not at the next launch. The two that can find a credential another tool saved — OpenCode Go, and the mainland GLM plan — count as ready, since nothing has to be pasted for those to work. The enabled set is stored, so a new case would otherwise be missing from every stored list and never appear at all; switching it on at every launch would override the user turning it off. What is remembered is which providers have been *offered* — the same decided-once shape `LoginItem` uses.
- Each CLI can be read more than one way, and which one is used is a setting ([UsageSource.swift](Sources/Pulse/UsageSource.swift), `AppSettings.source(for:)`). Codex has two routes; the primary Claude Code account has three, once `.desktopApp` is counted — see [ClaudeCodeUsageService.swift](Sources/Pulse/ClaudeCodeUsageService.swift) and [ClaudeDesktopSession.swift](Sources/Pulse/ClaudeDesktopSession.swift) below. `.automatic` is the default and should stay it: it takes the endpoint when it can and the other routes when it can't, which is what survives an expired token unnoticed. Pinning to one route means a failure is *reported* rather than quietly answered from elsewhere — that's the point of pinning.
- **The refresh interval is adaptive by default** ([AdaptiveRefresh.swift](Sources/Pulse/AdaptiveRefresh.swift)), between 2 and 30 minutes. A fixed minute spends the same requests at 3am as mid-session, on figures that haven't moved since last night. The wait is decided from: whether either CLI is writing its transcripts right now (`AgentActivity` — file *metadata* only, ~2ms over both trees, and the signal a menu-bar app can't have), whether the reported figures actually moved, whether the rail was hovered, whether the panel is even on screen, and low power / thermal / display-asleep. **Every signal is a reason to wait longer**, never shorter, so a new one can only save requests. Because the wait changes each pass, `UsageStore` schedules a one-shot timer and reschedules after every refresh rather than repeating on a fixed one.
  **The loop has to be able to restart itself, because the timer is not a promise.** `scheduleNext` only runs when a pass *finishes*, so a pass that never returns takes the whole schedule with it and nothing ever asks again — reported from the field as a panel twenty hours stale that came back to life the moment Claude Code was run in a terminal, which is the *activity* path calling `refresh()` while the timer path lay dead. Three things guard it now: a pass in flight longer than `passCeiling` is treated as gone and the next one is let through (on both the full and per-account paths, since both set the flag); `noteLooked` refreshes when the newest reading is older than twice the cadence chosen for it, not only when the cadence is slow; and `NSWorkspace.didWakeNotification` is observed as well as `screensDidWake`, which are different notifications and do not always arrive together. The exact stall was never reproduced — the process was gone by the time it was looked at — so this is written to recover whatever the cause, rather than to fix one guess.
  **Releasing a stalled pass is not the same as ending it, and that distinction is load-bearing.** The abandoned pass is never told it was abandoned: it is still awaiting its requests, and when they answer it writes into `usage` and clears the flags — which by then belong to a different pass. Measured before the fix: a ring clicked during a stall showed 90%, and six seconds later the ghost put 5% back, undoing the one refresh the user had asked for by hand; with three passes the older overwrote the newer and a third was let through under a live one. Every pass is stamped (`generation` / `currentPass`) and checks it is still current before writing anything or clearing any flag.
  **Never read is not overdue.** An unavailable reading carries no `observedAt`, so `isOverdue` answered yes for ever on a Mac where nothing is configured — or where every enabled provider is refusing, which includes one refusing *because* it is rate limiting. `noteLooked` runs on every ring the pointer crosses, so sweeping the rail sent one request per ring: measured, thirteen calls for twelve rings, which is the exact opposite of the rule that every signal here may only make it wait *longer*. There is a cooldown on it too, since a rail is crossed ring by ring several times a second.
  Comparing readings to detect movement must compare `windows` only — `observedAt` moves on every successful fetch, so including it reports a change every time and the loop never slows down.
- **Interpolating an `Int` into a localization key produces `%lld`, not `%@`.** A strings file written with `%@` then never matches and the text silently falls through to English — this shipped once in the refresh-interval labels. Interpolate a `String` instead: `.localized("\("\(count)") minutes")`.
- Messages on `ProviderUsage.Unavailability` are shared by both providers, so none of them may name one. They originally all said "Codex", which meant Claude Code reported "Codex is rate limiting these checks."
- **The figure can count down instead of up** (`AppSettings.showsRemaining`, off by default). The same reading either way — 12% used and 88% left are one fact — but which one a person wants at a glance is a matter of how they think about a budget, so it is offered rather than argued about. Spent is the default because that is what the providers themselves report.
  **Two things the arc must not do when it counts down.** A provider that has reported *nothing* had `usedFraction ?? 0` inverted into a full circle — measured by sampling the rendered circumference, 720 of 720 points coloured, and `pulseGood` green: "100% left, all fine" for a ring that knows nothing, during the first seconds after launch, when signed out, when waiting on a key, when rate limited. And a **spent** limit had no arc at all, since nothing left is nothing to draw — the most urgent state with the least ink, on a top rail whose figure is off by default. No reading now draws an empty track either way round, and spent fills the ring whichever way it counts.
  **The ring turns over with the figure and its colour does not.** A number reading 88% beside an arc drawn at 12% is one reading disagreeing with itself, so the arc shows what is left too; but colour on these rings means how close the limit is, and that does not change because the number was counted from the other end. A ring with a sliver left is a *small red arc*. Nothing about the layout changes — "100%" is the widest either way — so unlike the other panel settings this needs no `PanelMetrics` entry.
  **Both ends get the rounding rule, not just one.** Subtracting the used figure from 100 is tidier and wrong at the extremes: a window 99.6% spent would read "0% left" while there is still something there, which is the rule below told backwards. Each figure is held off both ends instead, so the two views need not sum to 100 — only one is ever on screen.
- **The word beside the figure has to follow the figure.** The card said "Used" whichever way it was counted, so a limit 88% gone read "12% Used" while the rail an inch away said "12% left" — the two halves of the panel contradicting each other, and the card stating the opposite of the truth. The accessibility value had the same fault.
- **Nothing used at all reads as 0%; anything used reads as at least 1%** (`UsageWindow.percentText`). The mark says so whether the figure does or not — the ring's arc has a round cap and the bar is a capsule, so the smallest non-zero reading still puts a dot of colour on screen, and "0%" beside it is the same number disagreeing with itself. The providers round this way too: Cursor reports 0.03% for a pool and its own page says 1%.
- **Colour means usage, not identity** ([UsageTint.swift](Sources/Pulse/UsageTint.swift)): green below 50%, amber to 75%, red above, and a deeper red once the limit is spent. Rings and progress bars were originally drawn in each provider's brand colour, which read as a status it never was — Claude Code's orange-red looked like a warning at 3% used. `Provider` deliberately no longer carries an accent colour; the icon carries the brand.
  **A colour can be chosen per account, and the default is not one** (`RingTint`, `AppSettings.ringTints`). Asked for by a user, and worth having — but it is opt-in, because choosing a fixed hue is choosing to give up the reading the rings exist for. **A spent limit still shows the spent colour whatever is chosen**: being blocked is not a matter of taste. The ring is *told* whether the limit is spent (`UsageRingView.isSpent`) rather than deciding it from the fraction — a provider says spent well short of 100%, and reading it off the percentage left a locked 87% window drawing a red figure beside a blue arc. It is the system's own colour well — any colour, with the eyedropper — rather than a handful of swatches: eight is not a choice, and the constraint that produced them (staying legible on the panel's black *and* on Liquid Glass) is a constraint on us, not on the person picking. Stored as hex, **converted through sRGB explicitly**: a colour picked in Display P3 answers its components in that space, and read back raw it would come out a different colour. Opacity is off — a translucent ring reads as a dim one, which already means "no reading".
- **"Spent" comes from the provider, not from the percentage.** Claude Code reports a `severity` and a `locked_reason` per limit; Codex reports `limit_reached` / `allowed` per group plus a top-level `rate_limit_reached_type` and `spend_control.reached`. Those are their judgement, and a spend limit's percentage can run past 100 anyway, at which point the ring is already full and only this can say so. An unrecognised `severity` value is treated as spent rather than fine — erring towards "you're blocked" is the safer way to be wrong. Codex's flags describe a whole *group*, which may hold both a 5-hour and a weekly window, so `markingSpent` pins the flag to the fullest window rather than smearing it across both.
  The spent state also recolours the figure beside the ring, not just the stroke: at ring size a fourth hue on a 4pt arc reads as the third one.
- The rail's ring shows one window per provider: by default whichever is closest to its limit, or a specific one pinned in that provider's settings (`AppSettings.pinnedWindows`, keyed by `UsageWindow.id`). The choice is resolved at display time in `FloatingUsagePanelView`, not baked in when the reading is fetched, so changing it takes effect immediately rather than at the next refresh. A pin that stops matching anything — a model that is no longer reported — falls back to the default instead of blanking the ring.
- [ProviderUsage.swift](Sources/Pulse/ProviderUsage.swift) — what a provider reports: a list of `UsageWindow`s plus a `State` of `.live` / `.stale` / `.unavailable(_)`. **Pulse never computes a percentage of its own.** The token budgets behind these limits aren't published, so anything derived from local token counts would be a guess presented as a fact; if a provider doesn't report a figure, the UI says so. (The money estimate below is the deliberate exception, and it is marked as one on screen.)
  Both `UsageWindow.Kind` and `ProviderUsage.Unavailability` are **cases, not strings**, and their text is built when displayed. A reading is taken once and shown much later, so storing the translation would freeze it in whichever language was current at fetch time — the same trap that caught the old sample data.
- [CodexUsageService.swift](Sources/Pulse/CodexUsageService.swift) — the default route is the one Codex's own client takes: read the OAuth credentials Codex already stored in `~/.codex/auth.json`, then `GET chatgpt.com/backend-api/wham/usage` for the account-wide windows plus any per-model limits. Nothing stays running, so it is quick, and it works even when the `codex` command isn't findable. Caveats: the endpoint is not public API and can change, and the stored token expires — Codex refreshes it while you use Codex, but nothing refreshes it for Pulse.
  When the token is missing or refused (401/403), it falls back to [CodexAppServer.swift](Sources/Pulse/CodexAppServer.swift), a JSON-RPC client for `codex app-server`. That is Codex's own documented protocol, it is signed in on its own terms so it renews credentials itself, and it pushes `account/rateLimits/updated`. The two answers have **different field names** (`used_percent`/`limit_window_seconds`/`reset_at` versus `usedPercent`/`windowDurationMins`/`resetsAt`), hence the two parsers.
  **The plan comes back as an internal tier name**, not the name on the plan — `prolite` is the 5× Pro tier. `CodexUsageService.planName` maps the ones we know and passes anything else through verbatim rather than blanking it: an unfamiliar name still beats no name, and it is the only clue left when a new tier appears.
  **Never assume a fixed pair of windows.** `primary`/`secondary` aren't tied to particular durations, and which exist depends on the plan — ChatGPT Pro has no 5-hour limit at all, only the tiers below it do. A window's kind is derived from its duration, and the UI renders however many come back.
  **SIGPIPE is ignored process-wide** (`AppDelegate`), and it has to be. Writing to a pipe whose far end has closed raises it, and its default is to kill the process — so the helper exiting, being killed with the terminal it was started from, or the user quitting Codex took Pulse down with it, leaving nothing in the log but `Terminated due to signal 13`. Ignored, the write returns `EPIPE` instead and `CodexAppServer.write(_:to:)` reads that as the helper being gone and drops it so the next call starts a fresh one. Reproduced both ways against a process that had already exited: unguarded the probe was killed before it could print a line, guarded it reported "Broken pipe" and carried on.
  Locating the executable for the fallback can't rely on `PATH`: a GUI app inherits almost none of it, so `CodexAppServer.locateCodex` checks the usual install locations, including versioned Node directories.
  **Proxies:** `URLSession` follows the system proxy settings automatically, so on a machine behind a VPN or proxy client the call rides that tunnel — which is what you want, since the endpoint may only be reachable through it. It also means a tunnel that stumbles surfaces as a Pulse error, typically `-1005 networkConnectionLost`, so transient `URLError`s are retried a couple of times before becoming an error in the UI. Note that `URLSessionConfiguration.connectionProxyDictionary` is empty even when a proxy is in use — it means "use the system defaults", not "no proxy", so don't read an empty dictionary as evidence of a direct connection.
- [ClaudeCodeUsageService.swift](Sources/Pulse/ClaudeCodeUsageService.swift) — the default route is the account's usage endpoint, `GET api.anthropic.com/api/oauth/usage`, using the OAuth credentials Claude Code already stored under the keychain service `Claude Code-credentials` (falling back to `~/.claude/.credentials.json`). Parse the response's `limits` array rather than the top-level `five_hour`/`seven_day` fields — only the array carries the per-model `weekly_scoped` windows. `kind` maps to the window (`session` is the 5-hour one) and `scope.model.display_name` names the model.
  The saved token expires in hours and **nothing here renews it**, so an unusable token — refused (401/403) or absent altogether — is tried next against the primary account's [ClaudeDesktopSession.swift](Sources/Pulse/ClaudeDesktopSession.swift), and only after that against [StatusLineHook.swift](Sources/Pulse/StatusLineHook.swift). **A network stumble, a rate limit or a server error skips Desktop entirely and goes straight to whatever the status line last captured**, on the same reasoning `UsageCache` runs on elsewhere: a network failure shouldn't hide a perfectly good captured reading, so that reading is preferred and the error is kept only in reserve, for when nothing was captured either. StatusLineHook is officially documented (code.claude.com/docs/en/statusline): Claude Code pipes a blob carrying `rate_limits.five_hour` / `.seven_day` to whatever command is registered as the status line, so Pulse registers itself — run as `Pulse --statusline` it banks the figures and prints a status line back. It is a **push, not a pull**: figures only refresh while a session runs, hence a capture more than ten minutes old (`freshFor`) reads `.stale` with an "as of" line rather than passing an old reading off as current. It carries no per-model windows, which is the other reason it isn't the primary route.
  **A window whose reset time has passed is dropped here too, not aged.** This route is a push: the figures only move while a session runs, so a Mac that hasn't run Claude Code since yesterday is still holding yesterday's blob, and any five-hour window in it reset long ago. Shown with an "as of" line it still reads as a limit you are inside, when it is a number about a window that no longer exists — and once every window in the blob has gone, `capturedUsage` returns nil and the caller says it is waiting on Claude Code instead of reporting a figure. `UsageCache` has had this rule from the start; this is the *other* place an old reading can come from and it went without, which is how a reset time 28 hours in the past reached the card. Found because the window-clock arc drew a full circle: 9% used looked plausible, a spent clock on a five-hour window did not.
  **The plan's name comes from a second endpoint**, `GET /api/oauth/profile` — the usage reply does not carry one, which is why this provider showed no plan at all while every other one did. `subscription_type` is preferred where a reply has it; otherwise `organization.rate_limit_tier`, which is where the **multiplier** lives: a Max plan is sold as 5× or 20× and those are different products, so `default_claude_max_5x` reads "Max 5x". Anything unfamiliar is passed through tidied rather than blanked, the same rule Codex's tier names follow. Only the plan-shaped fields are read — the same reply carries the account's name, its email address and its organisation's identifiers, which are the user's and no use to Pulse, exactly as with Antigravity's `GetUserStatus`. It is cached for six hours: a subscription changes about as often as somebody changes their mind about paying for one, while the refresh loop comes round every few minutes, and a failure is cached too so the plan can never cost the usage reading a retry every pass. The same reply also seeds [ClaudeAccountIdentity.swift](Sources/Pulse/ClaudeAccountIdentity.swift) with a fingerprint of whoever this token belongs to — banked here because by the time the desktop route below needs to ask that question, the token that would answer it directly has usually expired.
  A network failure prefers a captured reading over showing an error, since a stale number beats no number. Neither endpoint is public API; both can change without notice.
  **The status line hook edits the user's `~/.claude/settings.json`.** It backs the file up to `settings.json.pulse-backup` on first touch, remembers any status line command that was already there so it can chain to it and restore it on disconnect, and rewrites its own path on launch (`repairPathIfNeeded`) since rebuilding moves the executable.
  **An account Pulse signed in to itself never reaches either fallback.** `fetch(account:token:)` — what [UsageStore.swift](Sources/Pulse/UsageStore.swift) calls for every account but the primary — goes straight over HTTP with the token that account holds, and nowhere else: the status-line capture and the desktop session both belong to whichever account the CLI, or the desktop app, actually happens to be signed in to, which for an added account is not this one. `UsageSource.options(for:)` reflects the same rule by leaving `.desktopApp` off an added account's picker entirely, rather than offering a choice `fetchAdded` would silently ignore.
- [ClaudeDesktopSession.swift](Sources/Pulse/ClaudeDesktopSession.swift) — a third route to the **primary** Claude Code account's limits, for a session started from the desktop app rather than a terminal. The desktop app runs the same `claude` binary the CLI does but hands it a token through its own environment and renews that token itself, so it never writes the keychain item the endpoint route reads, and there is no terminal running to push a status line either. Measured on a Mac driven entirely through the desktop app for a day: the keychain item and the status-line blob were both frozen at the same minute — the last time `claude` had been run in a terminal — while transcripts went on being written every few minutes, so both of the other routes were quietly answering with yesterday's figures, and the cache made that look like a refresh button doing nothing. What it borrows is the desktop app's own login rather than a credential of Pulse's own: the app is Electron, so it keeps a Chromium cookie store and a `Safe Storage` key in the login keychain — the same two things [BrowserCookies.swift](Sources/Pulse/BrowserCookies.swift) already reads for Chrome and Edge — and only `claude.ai`'s `sessionKey`/`sessionKeyV3` cookies are ever read out of it.
  **Automatic use is gated on the keychain grant having already happened.** There is no way to ask the keychain for an item silently — `SecKeychainSetUserInteractionAllowed` is the only switch for that dialog and it is deprecated with no replacement — so [AppDelegate.swift](Sources/Pulse/AppDelegate.swift) asks for `Claude Safe Storage` once at launch, fenced three ways: only when a desktop cookie store actually exists, only when Claude Code is enabled and its source is Automatic or Desktop App, and only **once** — a refusal is a decision, and a menu-bar app asking again at every launch would be the worst version of this. After that, `.automatic` reads the remembered grant rather than raising the dialog itself; pinning `.desktopApp` in Settings calls `usage(for:)` directly instead, without checking whether the grant already happened, so a first-time pin can raise the dialog right there rather than waiting for the launch-time ask. A grant that stops working is asked about again rather than treated as asked-and-refused: the keychain ties the allowance to the code signature, and Pulse is ad-hoc signed, so every update is a different app as far as the ACL is concerned.
  **Only a live reading is worth interrupting the chain for.** A signed-out session or a refusal leaves the older routes their turn — between a live nothing and a dated something, the dated something is what the panel is for.
  **The two apps can be signed in as different people, and only a comparison that comes out wrong stops the substitution.** [ClaudeAccountIdentity.swift](Sources/Pulse/ClaudeAccountIdentity.swift) compares this session's account/organisation/email against whatever the CLI's own token last said about itself, captured in passing by the profile call `ClaudePlan` already makes every six hours — by the time the desktop route is needed the CLI's token has usually expired and can't be asked directly. A comparison with nothing on one side is **not** a mismatch: someone who has only ever used the desktop app may never have had a working CLI token on this Mac, and refusing the route until one appeared would withhold it from exactly the person it exists for. A pinned `.desktopApp` skips the comparison entirely — asked for the desktop app's session, it gets the desktop app's session.
  **Not public API**, the same caveat the endpoint route carries: `/api/bootstrap` and `/api/organizations/{id}/usage` are what the web client itself calls. The organisation asked about is the one the app is actually in front of (its `lastActiveOrg` cookie), not the first one the account belongs to, since one account can sit in more than one organisation and their limits are different limits. The call rides its own ephemeral `URLSession` rather than the shared one, so a `Set-Cookie` on these replies is never picked up and carried along on Pulse's other requests to the same hosts — the session belongs to the desktop app and is borrowed for the length of one call, not kept.
- [AntigravityUsageService.swift](Sources/Pulse/AntigravityUsageService.swift) — the odd one out, and the only route it has. Antigravity's editor starts a `language_server` of its own and talks to it over HTTPS on the loopback interface; that process is the only thing that knows the quota, so **these figures exist only while the app is open** — which `.antigravityNotRunning` says plainly rather than dressing up as a failure. Three things are discovered and **none may be assumed**: the process (inside the app bundle, not on `PATH`, and matched on `/Antigravity.app/` because `language_server` is Codeium's binary and its other editors use the same name), the port (the app starts it with `--https_server_port 0` — "take any free one", so it differs every launch), and a per-launch CSRF token from the command line, sent as `x-codeium-csrf-token`. It listens on more than one port and does not advertise which speaks this, so they are simply tried in turn.
  The RPC is `exa.language_server_pb.LanguageServerService/RetrieveUserQuotaSummary`, POSTed with `{}`. **It reports what is left, not what is gone** — `remainingFraction: 1` means nothing used — and it is the only provider that does, so the inversion happens here and everything downstream stays in terms of what is spent. The reply nests `groups[].buckets[]`, each bucket carrying `bucketId` (stable, so it can be pinned), `window` (`5h` / `weekly`), `remainingFraction` and a real `resetTime` timestamp — no reset time has to be dug out of prose. The group's name becomes the window's `scope` with a trailing "models" trimmed, so rows read "5-hour limit · Gemini". A bucket whose `window` can't be read is **left out rather than guessed at**: a window with no length can't be named or sorted, and inventing one would put a figure under a heading that isn't true.
  **The plan's name comes from a second call**, `GetUserStatus` — the quota reply doesn't carry it. Only `planName` is decoded from it: the same reply also holds the account's name and email address, which are the user's and no use to Pulse.
  **There is nothing else to read, and this was checked rather than assumed.** Of the 306 methods the language server exposes, not one has "usage" or "credit" in its name; `GetUserAnalyticsSummary` answers `{}`; `~/.antigravity` holds only binaries and extensions; and the editor's `state.vscdb` keeps conversation titles and two sentinel values under `modelCredits`, no token counts anywhere. So the spending history, the money estimate and the activity mark genuinely cannot be built for Antigravity — they are built from per-model token counts, and those do not exist to be read. Antigravity also reports a monthly credit *allowance*, never a balance, which is why `creditBalance` stays nil: an allowance shown there would read as what is left.
  The server signs its own certificate, so `LoopbackTrust` accepts it — and only for `127.0.0.1`. Anything else is refused exactly as it would be anywhere else in the app.
- [CursorUsageService.swift](Sources/Pulse/CursorUsageService.swift) / [CursorAppLogin.swift](Sources/Pulse/CursorAppLogin.swift) — the account's limits from `GET cursor.com/api/usage-summary`, undocumented like the two CLI routes.
  **The cookie it needs is not stored anywhere — it is built.** Cursor's website authenticates with a `WorkosCursorSessionToken` cookie rather than a bearer header, and the obvious way to get one is to go and read the browser's cookie jar, which means touching Safari's and Chrome's stores for every domain they hold. There is no need: the editor keeps its own OAuth token in the SQLite database VS Code keeps global state in (`~/Library/Application Support/Cursor/User/globalStorage/state.vscdb`, `ItemTable` keyed `cursorAuth/accessToken`), the account id is the tail of that token's own `sub` claim after the `|`, and the cookie's value is **that id and the token joined by `::`**, percent-encoded. So this borrows a login the same way the Claude Code and Codex routes do, and Pulse still holds no credential of its own. Opened read-only and in place: Cursor is usually running, so the database is in WAL mode and its `-wal`/`-shm` sidecars belong to that process — copying the file aside takes the main database without the journal holding the newest writes. The row is normally TEXT but has been seen as a BLOB, and when it is, it is UTF-16 with no byte-order mark; read as UTF-8 that yields the token with a null after every character, which parses as nothing and explains itself to nobody.
  **What the plan includes is two pools, not one**, which is how Cursor's own account page draws it: `autoPercentUsed` is Cursor's own models (Composer, Cursor Grok) and `apiPercentUsed` is everything else, and spending past the first eats into the second. They are reported as two windows scoped "Cursor Models" and "Other Models" — the page's own labels. The first cut of this shipped a single combined window and was wrong for exactly the reason a combined figure is always wrong: it cannot say which of the two is about to run out.
  **Those fields are percentages, not fractions** — 0.0267 means 0.0267%, not 2.67% — and that was settled by arithmetic rather than taken on trust, since a fraction read as a percentage is a hundredfold error either way. On an account 12¢ in, the three percentages imply pools of $450 for Cursor's models and $22.50 for the rest, summing to a $472.50 total that matches `totalPercentUsed` to the cent. Three numbers that agree are a system, not a coincidence.
  **`plan.used` / `plan.limit` is a different denominator and must not sit beside them** — it is the plan's cash value, $20 on Pro, against pools worth $472.50, so shown as a third bar it reads as a contradiction. It is used for the extra-spend limit, as the fallback when an account reports no pools at all, and as the `creditBalance` (`plan.remaining` is a real balance, not an allowance, which is why this provider reports one and Antigravity doesn't). A team account's `pooled` / `onDemand` stand in for the individual pair.
- [GrokBotUsageService.swift](Sources/Pulse/GrokBotUsageService.swift) — Grok Bot's weekly allowance, `POST cursor.com/api/dashboard/get-sand-usage-status` with the cookie [CursorAppLogin.swift](Sources/Pulse/CursorAppLogin.swift) already makes. Cursor's own protocol calls it "Sand".
  **A ring of its own, though the credential is Cursor's.** Grok Bot is xAI's, sold through Cursor and billed against that account — so it borrows Cursor's login, but it is not a share of Cursor's monthly bill the way the two model pools are. It shipped as a fourth row on Cursor's card first, and the question that came straight back was "where is Grok Bot", asked while looking at the Grok pane — which is the *other* Grok. A name people use is worth a place on the rail.
  **And it is the other Grok.** [GrokUsageService.swift](Sources/Pulse/GrokUsageService.swift) reads the weekly pool a SuperGrok plan spends across every xAI product; this reads an allowance that arrives with a Cursor subscription. Two companies' bills, one brand, so the two share no credential, no endpoint and **no mark**: Grok carries `grok.svg` and Grok Bot the parent brand's `xai.svg`, which is the one thing telling them apart on a rail carrying both.
  **The reply states no reset and no length**, and that was checked rather than assumed — Cursor's dashboard REST call and the Connect RPC behind it (`api2.cursor.sh/aiserver.v1.DashboardService/GetSandUsageStatus`) answer byte for byte, and neither carries the `nextResetTimestampUtc` a reference implementation decodes. So the field is read where a reply offers one, the row simply has no reset line where it does not, and the seven days are a **sort key** (`reportsLength: false`) exactly as Kimi's rolling week and Cursor's own billing cycle are. That it is weekly is xAI's own word (docs.x.ai/grok-bot/faq), not an inference from a start stamp.
  **Deriving the reset from `currentPeriodStart` + a week was considered and is wrong, and the vendor's own client is the proof.** Inside `Grok Bot.app` (`Contents/Resources/app.asar`): `nextResetMs: n != null && Number.isFinite(n) && n > 0 ? n : null` — where `n` is `nextResetTimestampUtc`. It falls back to nothing, never to the period start. The same bundle carries the schema, and both stamps are proto3 **message** fields (`{no:1,name:"current_period_start",kind:"message"}`, `{no:2,name:"next_reset_timestamp_utc",kind:"message"}`), which have explicit presence — so an absent one is genuinely unset rather than a zero the serialiser dropped, unlike Grok's `credit_usage_percent`. Showing a reset here would put Pulse ahead of the app the figure comes from.
  **That combination found a real bug one layer up.** `UsageDetailCard.resetText` fell back to `lengthText` whenever `resetsAt` was nil — printing "7 days" for a length nobody reported, which is precisely what `reportsLength` exists to prevent. No shipped window had reached it, because every other one with a chosen length also had a reset. It says nothing now.
  **Nothing included is not nothing used.** An account with no Grok Bot allowance answers 0% as well, with the rest of the reply given over to upgrade marketing — drawn literally that is a full green ring for something the account does not have, the trap Copilot's unissued quotas set. `hasNonZeroIncludedLimit` must say yes, `includedLimitZero` must not, and a seat drawing on an organisation's pot (`usesPooledEnterpriseAllowance`) has no personal share at all. Those three come back as **`.grokBotNotIncluded`, not `.noLimitsReported`**: a plan that doesn't include it has answered completely, and "no limits reported" sends someone looking for a fault that isn't there.
  **A second Grok Bot account is signed in to, and it is not OAuth** ([CursorWebLogin.swift](Sources/Pulse/CursorWebLogin.swift)). Cursor publishes no authorize/token pair for a third party to drive; what it has is a login page taking a challenge and a nonce, and a polling endpoint that hands the tokens over once the browser has finished — `cursor.com/loginDeepControl?challenge=…&uuid=…` then `api2.cursor.sh/auth/poll?uuid=…&verifier=…`. **404 there means "not yet", not "wrong address"**: the nonce has nothing filed against it until the page completes, and Cursor's own client retries on exactly that status. Only a 403 carrying an `error` ends the attempt.
  The proof key *is* PKCE's, and the one detail worth getting right is which value is hashed: the verifier is 32 random bytes base64url-encoded, and the challenge is the base64url of the SHA-256 of **that encoded string**, not of the raw bytes. Read out of Cursor's own client (`Grok Bot.app/Contents/Resources/app.asar`) rather than inferred, for the reason `OAuthLogin` states — a flow with one parameter wrong fails in a way that looks like the user's fault. Nothing redirects back to this Mac, so there is no loopback port to bind and none to collide with Cursor's own sign-in, and there is no code to type either: the browser is the whole interaction.
  **These tokens run sixty days** (measured, from the `exp` of this Mac's own), which is why an added account here does not need the renewal a Codex or Claude Code login needs every few hours. No refresh endpoint exists in Cursor's client, so when one does age out `fetchAdded` reports `.signedOut` and the remedy is to sign in again — twice a year, and honest.
  **Cursor itself is deliberately not multi-account.** The same sign-in would work, but Cursor's usage summary is read from the editor's own stored login and a second account has no editor behind it; Grok Bot needs nothing but the token.
  **Only the standalone app counts as installed** (`Provider.installedOnThisMac`). Grok Bot is also used inside Cursor, but a Cursor login is no evidence the plan *includes* it — keyed on that, every Cursor user's first run would carry a ring that says "your plan doesn't include this", which is the greyed-out rail that function exists to avoid.
- [OpenCodeGoUsageService.swift](Sources/Pulse/OpenCodeGoUsageService.swift) — the OpenCode Go plan, and **the only provider Pulse holds a credential for.** The other three borrow a login their own tool already stored; this one is reached with a bearer token the user pastes into Settings, kept encrypted by [APIKeyStore.swift](Sources/Pulse/APIKeyStore.swift) — *not* `UserDefaults`, which is a plist any process running as that user can read.
  **Two places the key can come from, in this order:** a key pasted into Settings, then whatever OpenCode saved for itself in `~/.local/share/opencode/auth.json`. The entered one wins — otherwise a stale key left behind by OpenCode would quietly override a deliberate choice — and the fallback means anyone already signed in there configures nothing.
  A key the service refuses reports `.openCodeKeyRefused`, **not** `.signInRequired`: that message names Codex, and a message naming the wrong provider is the trap the rest of `Unavailability` was fixed for once already.
  `GET /zen/go/v1/usage` returns `usage.{rolling,weekly,monthly}`, each with `status`, `percent` (how much is **gone**, unlike Antigravity) and `resetsAt`. Undocumented — OpenCode's own docs cover only the model endpoints — so it can change without notice. A `status` other than `ok` is treated as spent, erring towards "you're blocked".
  **The window the reply calls `rolling` is the five-hour one** — the reset it reports lands five hours out — so it is shown as "5-hour limit" like everywhere else, and only its *id* keeps the provider's key, which is what a pinned window is matched on. `Kind` gained `.monthly` alone, since a billing period had nowhere to map. `windowSeconds` orders the rows; only the reset stamp is ever displayed.
  `opencode stats` proves the CLI keeps sessions with token counts and cost, so a spending history *is* possible here later, unlike Antigravity. It lives in OpenCode's own store rather than the JSONL both other CLIs write, which is why `keepsLocalTranscripts` is false for now.
- [KimiCodeUsageService.swift](Sources/Pulse/KimiCodeUsageService.swift) — `GET api.kimi.com/coding/v1/usages`, with a key the user enters. Documented, unlike the two CLI routes.
  **The reply holds two kinds of limit and they are not the same figure.** `limits[]` are windows the service actually times, each stating a `duration` and a `timeUnit` — read as given, and an unrecognised unit drops that entry rather than being guessed at. `usage` is the weekly allowance — the reply gives it a reset time and no length, and because the window rolls, the reset lands anywhere inside the week and says nothing about how long it runs. Its seconds sort it after the shorter windows and are never displayed.
  Every count arrives as a **string**, and `limits[].detail` reports what is *left* with no `used` field at all, so the spend is `limit - remaining` there and `used` where that is given. `membership.level` is the plan, tidied from `LEVEL_INTERMEDIATE` to "Intermediate" and passed through when unfamiliar. `parallel.limit` is how many requests may run at once, not a balance, and `totalQuota` comes back empty — neither becomes `creditBalance`.
- [ZaiUsageService.swift](Sources/Pulse/ZaiUsageService.swift) — the GLM Coding Plan, `GET {host}/api/monitor/usage/quota/limit` with a pasted key. **Two providers, one service**: `api.z.ai` and `open.bigmodel.cn` are one company's international and mainland storefronts, answering the same JSON on different hosts — but they are separate accounts with separate keys, and a key for one is refused by the other. CodexBar models this as one provider with a region switch; each gets its own ring here, because someone with only the mainland plan should not have to know an international one exists in order to configure theirs.
  **The reply carries a status of its own** — `success` and `code`, both of which must say 200 *even when HTTP did*. A refused key arrives as a perfectly good HTTP 200 with `success: false`, so reading only the status line would report an empty plan rather than a bad key.
  **A whole-number `percentage` is the fallback, not the answer.** Where the reply also gives counts, the spend is worked out from them: `remaining` is what is *left* so the spend is the difference, and `currentValue` is the spend directly and wins when both are present. Measured: a limit stating `percentage: 7` with `usage: 1000, remaining: 247` is 75% gone, and the stated figure is simply wrong.
  **A window's length is a `unit` code times a `number`** (1=day, 3=hour, 5=minute, 6=week); an unrecognised unit means the length can't be read, and that window is **dropped rather than guessed at** — the same rule Antigravity's buckets follow. The one exception is the MCP lane, which reports its monthly allowance as "1 minute": a marker, not a duration, and taken literally it sorts above a five-hour limit and claims to reset every minute. `nextResetTime` is epoch **milliseconds**.
  **A limit with no figure at all is dropped, not drawn at 0%** — the counts are preferred where present, `percentage` is the fallback, and neither means there is no reading rather than a reading of nothing. An envelope refusal is likewise not automatically a bad key: a 500 or a rate limit arrives the same way, and saying "check your key" sends the user after a credential that is fine.
  Numbers are decoded as `Double` rather than `Int` on purpose: a service that starts sending `12.5` where it sent `12` would otherwise fail the whole reply and blank the ring over a figure that is perfectly usable.
  **Reading a key out of a file needs `whitespacesAndNewlines` and a real newline split.** `split(separator: "\n")` does not cut a CRLF file at all — Swift counts `\r\n` as one Character — and `CharacterSet.whitespaces` contains neither CR nor LF. `URLRequest.setValue` then *silently discards* a header value containing a newline, so the request went out with no `Authorization`, came back 401, and was reported as a refused key: about a key that was correct, in a Settings field that was empty because it came from a file.
  The mainland route also reads a key already on this Mac (`~/.coding-relay/glm-api-key`, `~/.config/bigmodel/api_key`, `~/.config/zhipu/api_key`, first line only), which is both a fallback and the first-run evidence that this Mac is set up for it. **Never consulted for the international route** — quietly sending a BigModel key to `api.z.ai` reports a refused key for a plan the user doesn't have.
- [MiniMaxUsageService.swift](Sources/Pulse/MiniMaxUsageService.swift) — the MiniMax Coding Plan, `GET {host}/v1/token_plan/remains` with a pasted key, falling back to the older `/v1/api/openplatform/coding_plan/remains` on a 404 (an older account, not a failure). **Two providers again**, `api.minimax.io` and `api.minimaxi.com`, for the same reason as the GLM plan. Three things about the reply:
  **It reports what is *left*.** `current_*_remaining_percent` at 96 means 4% spent — Antigravity is the only other provider that does this, and the inversion happens here so everything downstream stays in terms of what is gone.
  **Every figure can be a string or a number**, the same field in different replies (CodexBar's own two fixtures disagree: `"96"` and `75`). Reading only one shape blanks a window for whichever accounts get the other.
  **Lanes exist that the subscription doesn't include** — status 3, nothing issued, 100% remaining, a video lane on a plan with no video. Read literally that is a ring pinned at 0% for something the account cannot use, so they are left out. The same shape covers a genuinely unlimited lane, which has no percentage worth showing either.
  **`*_usage_count` is the quota that is *left*, not the quota used** — the name says the opposite of what it holds, and reading it as a spend inverts every figure on the card. It is the fallback when the percentages are absent, which is the shape the older endpoint returns. The payload is likewise not always under `data`; some replies put it at the root, and reading only `data` reported a good account as having no limits.
  Each model gives up to two windows. The short one's length is measured from its own timestamps (5 hours, in every reply seen) and is **dropped when they are absent** rather than assumed; the weekly one names its own length so it survives that. `base_resp.status_code` is the service's verdict and is not the HTTP status — a refused key is a perfectly good 200.
- [CopilotUsageService.swift](Sources/Pulse/CopilotUsageService.swift) / [GitHubDeviceLogin.swift](Sources/Pulse/GitHubDeviceLogin.swift) — GitHub Copilot, from `GET api.github.com/copilot_internal/user` with the editor headers its own plugins send. Not public API; `percent_remaining` is what is **left**, so the inversion happens here.
  **A sign-in rather than a pasted token, and that is a security decision.** The endpoint accepts any GitHub OAuth token — the one `gh` already holds works, verified — so a key field would have been the cheap route. That token carries `repo` and `workflow`: the run of someone's source code, handed over to draw a percentage. The device flow asks for `read:user` and nothing else. Pulse can't register an OAuth app with GitHub, so it drives the VS Code plugin's public client, with the same consequence as the other borrowed clients — the consent page names the editor.
  **Three quotas come back, not two** — `completions`, `chat` and `premium_interactions` — and which of them an account has depends on the plan. A reference implementation this was checked against reads only the latter two; on a free plan `completions` is the largest allowance of the three (2,000 against chat's 200), so leaving it out hides most of what the account has.
  **A quota the plan doesn't include must be dropped, not drawn.** It arrives with `has_quota: false`, nothing issued, and `percent_remaining: 0` — which read literally is a full red ring for something the account never had. `has_quota` says it outright; the zero entitlement is checked too, since older replies omit the flag. Unlimited lanes are dropped for the same reason as everywhere else: there is no share to show.
  **The verification link must not carry the code, and that is a security property rather than a missing feature.** RFC 8628 has a field for a pre-filled address (`verification_uri_complete`) and GitHub deliberately does not send one; its page says why in as many words — *"Never use a code sent by someone else"*. Pre-filling **is** the device-code phishing attack: the attacker sends a link carrying *their* code, the victim approves it, and the attacker holds an authorised token for the victim's account. Typing the code is what makes the person consent to *this* device rather than to a link they were handed. A `user_code` parameter was tried and is ignored; it is not kept, because it would do nothing except give Pulse's link the shape of the attack. The code goes on the clipboard instead — one paste, consent still in the right place. The `verification_uri_complete` field is read if a service ever offers one, since that is the service's own decision to make.
  The reset is one date for the whole account (`quota_reset_date_utc`) and lands on the first of a month — the per-snapshot `quota_reset_at` is 0 and useless. A calendar month is 28 to 31 days, so `reportsLength` is false and the clock arc draws nothing.
- [GrokUsageService.swift](Sources/Pulse/GrokUsageService.swift) — the Grok account's weekly pool, `GET cli-chat-proxy.grok.com/v1/billing?format=credits` with the OIDC login Grok Build's CLI stored in `~/.grok/auth.json`. Another borrowed login rather than a credential of Pulse's own, and not public API — it is what the CLI itself calls.
  **The provider is called Grok, not Grok Build, because the pool is the account's.** Since June 2026 a paid plan spends one weekly pool across every Grok product — the web chat, Imagine, voice, the API and the CLI alike — and the reply proves it rather than leaving it to be inferred: `productUsage` lists `GrokChat` beside `GrokTasks`. So there is no CLI-specific figure to show, and naming the ring after the CLI would claim one. The breakdown is **not** drawn as separate windows either: they are shares of one limit, and four rows would read as four limits.
  **The header is what selects the shape of the reply.** Without `x-xai-token-auth: xai-grok-cli` the same path answers the enterprise credit form instead — `monthlyLimit`, `onDemandCap`, a history of billing cycles — which on a personal plan is zeroes throughout. A denominator of nothing is not a reading, and it took a while to notice that the empty answer was the wrong *question*.

Treating a missing figure as "no reading" would blank the ring for the first hours of every week. The `USAGE_PERIOD_TYPE_WEEKLY` enum is theirs to rename; the subtraction is not.

The stored token lasts about six hours and only the CLI renews it, exactly as with Codex, so an aged-out login is reported rather than worked around: `.grokLoginExpired` against `.grokSignInRequired`, two cases rather than one because "signed in, and it went stale" is a different instruction from "never signed in".
- **A provider that is switched off is not fetched at all.** It was, once: five requests went out every pass and only the enabled ones were ever drawn, which spends someone else's rate limit and reads a credential for a figure nobody will see. A provider's own pane in Settings can still refresh it by name while it is off — a deliberate press is a different thing from a timer.
- **Keys entered in Settings live in `keys.dat`**, AES-GCM boxes in Pulse's own folder, owner-only, with the key derived from the Mac rather than stored ([APIKeyStore.swift](Sources/Pulse/APIKeyStore.swift)). They are read once per launch rather than once per refresh pass — `UsageStore.loadAPIKeys` runs at start, when settings change, and when a key is saved.
- **Two providers now need a key**, so `Unavailability` has `.apiKeyMissing` / `.apiKeyRefused` rather than a pair named after whichever came first. Same rule as the rest of that enum: a shared message may not name one provider.
- [UsageCache.swift](Sources/Pulse/UsageCache.swift) — **the last good reading from each provider, so a refusal shows numbers with a date on them instead of an error with nothing.** Everything Pulse talks to says no sometimes: the endpoint is undocumented and rate limits, saved tokens expire, a VPN drops a connection. These figures move in percent over hours, so the last answer is very nearly the right one. Two rules keep it honest: only `.live` readings are stored and they come back marked `.stale` (which is what puts the "as of" line on the card), and a window whose **reset time has passed is dropped rather than aged** — it hasn't gone stale, it has reset, and what it says is not an old version of the truth but a number about a window that no longer exists. If every window has reset, the error is reported as before. A 24h cap backstops windows that never say when they reset.
  **A missing credential is not papered over.** The cache exists for refusals that pass — rate limits, expired tokens, a dropped connection — but when the key has been *deleted* there is nothing to come back to, and showing yesterday's percentages for up to a day while Settings holds an empty field hides the one thing the user needs told. `.apiKeyMissing`, `.ollamaSessionMissing` and `.signedOut` are reported as they are.
  **It is also what the rail opens with.** `UsageStore.start` puts the last reading on screen before the first request has gone out — otherwise every ring is blank for as long as the slowest provider takes to answer, which on a cold start reads as an app that hasn't finished loading. The same two rules make that safe: it arrives marked `.stale` so the card says when it was taken, and a window that has since reset is dropped rather than aged. A fetch that has already landed is never undone by it. `reconciled(_:)` prefers whichever reading was actually taken later, so this only ever fills gaps.
- [UsageStore.swift](Sources/Pulse/UsageStore.swift) — `@Observable`, owns the 60s refresh loop (the interval the Codex CLI itself uses).

- **`windowSeconds` is not evidence that a length was reported** (`UsageWindow.reportsLength`). Some windows carry a length chosen so the row sorts: Kimi's weekly allowance states a reset and no length and rolls, and Cursor's pools reset with a billing cycle of 28 to 31 days stored as a flat 30. Both are fine to order by and are never displayed — but the window clock divides by that number, and `windowSeconds > 0` cannot tell a measurement from a sort key. So the window says which it is, and the clock draws nothing where the length was chosen rather than read.

**Spending history and what a limit is worth (settings only):**
- Neither provider reports money, or any per-day history. Both of those are reconstructed from the transcripts their CLIs leave on disk — `~/.claude/projects/**/*.jsonl` and `~/.codex/sessions/**/*.jsonl` — priced at the providers' published API rates.
- [ModelPrices.swift](Sources/Pulse/ModelPrices.swift) — pulls `https://models.dev/api.json`, keeps only the `anthropic` and `openai` entries (model ids are unique within a provider, **not** across all 200-odd of them), caches them for a day. A model with no published price is left out of the cost and reported separately; it is never given a plausible rate.
- [UsageLedger.swift](Sources/Pulse/UsageLedger.swift) — reads the transcripts and adds them up. Notes:
  - The two providers count differently. Claude Code's `input_tokens` **excludes** cached tokens (they sit in `cache_creation_input_tokens`/`cache_read_input_tokens`); Codex's `input_tokens` **includes** them, with `cached_input_tokens` as the subset. Both are normalised to uncached/cache-write/cache-read/output before pricing, or the cache read gets billed at the input rate.
  - Codex reports a **running total for the session**, not a figure per turn, so readings are differenced. Summing its own per-turn `last_token_usage` double-counts — measured at 6% high on one long session. The running total only ever climbs, which is what makes the differences safe.
  - Buckets are **quarter-hours**, not days, because a five-hour window opens and closes inside one. Days are rolled up from them.
  - The per-file cache is keyed on size + modification date, and the **filename carries the bucket format** (`ledger-2-*.json`). Changing the key shape without changing the filename leaves old entries parsing as nothing, silently.
  - Cost is worked out **after** the cache, from tokens-per-model — so a price change costs nothing to apply instead of a few hundred megabytes of rescanning.
  - Verified against an independent implementation of the same arithmetic: both agreed to the cent ($235.52 / 413,932,186 tokens). Do that again after changing the counting.
- [BurnRate.swift](Sources/Pulse/BurnRate.swift) — **whether a limit will outlast its own window** (`AppSettings.showsForecast`, off by default). One line under each: "expected to last the window", or roughly when it runs out. **It rides on `PanelMetrics`, unlike the other two card settings**: it adds a fourth line under every limit, and the panel's frame is worked out from `DetailCardLayout` before SwiftUI lays anything out — left out of that budget, a top-docked card with five limits ran 84pt past the window and was sliced flat against its edge. Off by default for the same reason the window clock is: it is the one line on that card the provider did not report, and a projection nobody asked for, sitting under a reported figure, invites being read as one.
  **Everything comes from one reading, and that was not the first design.** How much is gone and how far through the window the clock is are both in it already — the second is what draws the window-clock arc — so the rate is the first divided by the second. This kept the last two dozen readings of every window in a file and measured a *trailing* rate instead, which is more responsive: it sees a change of pace, where an average since the window opened cannot. Measured over the same bursty five-hour window, that responsiveness is not worth its cost — the trailing estimate ranged over a factor of **24**, the cumulative one over 9-13, and the cumulative one needs no storage, no sampling and no reset detection at all. A window that has turned over simply reports a small elapsed share again. The idea is CodexBar's `UsagePace`; the arithmetic was checked against this machine's transcripts before it was adopted, and `UsageTrail` was deleted.
  **The pace itself was shown and then taken out**, and the reason generalises. It read as a balance: "8% in reserve" under a line saying "20% used" is read as *8% left*, when 80% is left — the opposite of the truth, not merely unclear. Every wording tried had the same problem, because the number is a comparison against a quantity that isn't on the card. The verdict already answers the question it was supporting, so it went; a figure nobody can read without being taught it first is worse than no figure.
  **The verdict says it is a projection** — "expected to last", "预计可用至本轮重置". Every other line on that card is a figure the provider reported, and on the one that isn't, reading as though it were a fact is the wrong claim. The time is rounded to a quarter hour and shown **only when it lands before the reset** *and* inside two hours: if the window resets first there is no exhaustion to predict. Note the Chinese takes its hedge from the rounding word alone — "预计 约 30 分钟" says it twice.
  `elapsedFraction` is what guards the division: it already refuses a window whose length was *chosen to sort by* rather than reported, which is exactly the length this would otherwise divide by. A separate floor stops a barely-open window being divided into — early on the elapsed share is so small that one burst projects an exhaustion six days out, which is how a five-hour window once read 9,574 minutes.
  Usage is extremely bursty — over three days of this machine's transcripts, 3% of five-minute slots had any activity at all and the busiest was six times the median — so anything here that reads as precise is wrong.
  **Every provider gets it, and none of them is named anywhere.** What it needs is a percentage, a reset and a length the provider actually stated, so `BurnRate` refuses the windows that lack one rather than being told in advance which those are: Kimi's rolling weekly allowance, Cursor's billing cycle and Copilot's calendar month all carry a length chosen to sort by, and all three fall out on their own. A list of providers would have had to be kept in step with that by hand.
  **Beyond the horizon the verdict is still said, without the time.** It was silent there once, which showed the good news and hid the bad — and a weekly window's exhaustion is nearly always further out than two hours, so that was most of the warnings there are.
- [BudgetEstimate.swift](Sources/Pulse/BudgetEstimate.swift) — **the one inferred number in the app.** The providers report a percentage and never what the rest is worth; the local logs say what was spent over the same stretch, so dividing gives the window a price. It is labelled an estimate wherever it appears, sits in its own settings group with its provenance written underneath, and is **withheld rather than guessed** when the inputs can't carry it: under 2% used the providers' whole-number percentages swamp the answer, logs that start after the window opened miss part of the spend, and a window **scoped to one model** can't be divided into the period's whole spend at all — that priced a 2%-used Fable window at ten thousand dollars, because the money in it had gone through Opus.
  Work done on another machine is invisible to this and pulls every figure low. Nothing can detect it; the caption says so.
- [AccountUsageCard.swift](Sources/Pulse/AccountUsageCard.swift) — the history card. A grid of figures rather than a list of rows: numbers as settings rows are lines read in order, the same numbers in a grid are one glance. Each cell carries **both** the money and the tokens for its span — split across separate cells they looked like separate facts and left the reader pairing them up by eye, when they are one fact: what went through, and what it was worth. **Reading a session out of the browser** ([BrowserCookies.swift](Sources/Pulse/BrowserCookies.swift)):
- Only Ollama Cloud needs this, and only because it has no quota API at all — the figures come from a signed-in page, so a browser session is the only credential there is. - **One host, and only the names that authenticate.** The caller passes a filter — Ollama's is the contributor's `OllamaSessionCookie.normalize`, which keeps four session names and drops analytics and everything else — and nothing that fails it survives the call. Nothing is stored here; what comes back goes straight into `APIKeyStore`.
  **"One host" is the host, its dot-form and its subdomains — never a suffix match.** Firefox and Chromium are queried that way in SQL; Safari's binary parser tested `url.hasSuffix(host)`, so asking for `ollama.com` also returned `notollama.com` and `evil-ollama.com`, whose values would have been joined into the header sent to the real one. Verified against a `binarycookies` file built for the purpose.
  **A repeated cookie name is not a malformed cookie.** Every browser store routinely holds both a host-only and a domain row for the same session name, and the host match returns both on purpose — so throwing on the duplicate discarded the *whole browser* (the call site takes it through `try?`) and moved on to the next one without a word, reporting a session read from a browser the user had never signed in at. The first wins, as it does in any cookie header. This is the failure mode the feature is prone to and the one it keeps finding new ways to produce: **a wrong lookup reads as an empty one.**
- **The default browser is tried first, whatever it costs.** That is a decision over the tidier-looking alternative of trying the free ones first: the browser the user opens links with is where they are actually signed in, and another browser may hold a session months out of date — finding *that* is worse than a prompt. Firefox is plain SQLite and costs nothing. Safari's file is inside its container and needs **Full Disk Access, which is granted per application** — so a `swift run` build cannot have it and only the bundled app can. Chromium keeps its key in the login keychain, so it raises the "Pulse wants to use your confidential information" prompt; the row says which browser it is about to open and whether it will ask, because being told a second beforehand is the difference between a step and a scare. The default is found through LaunchServices rather than guessed from what is installed.
- **A browser can be named instead** (`AppSettings.sessionBrowsers`, per account), and naming one means *only* that one is opened — the same bargain `UsageSource` makes: pinning is what turns a quiet answer from somewhere else into a reported failure. Only installed browsers are offered; one that isn't there is a choice that can only fail.
- **A browser's keychain service is not its display name.** Edge is shown as "Edge" and stores its key under `Microsoft Edge Safe Storage`, so building the service name from the display name found nothing, failed *silently*, and fell through to the next browser — which then reported having read the session from one the user had never signed in to. Each name is written out (`Browser.keychainService`) and checked against the machine rather than derived. That is the whole class of bug this feature is prone to: a wrong lookup reads as an empty one.
- **Both parsers are driven against data built on purpose**, because a binary format and a cipher are exactly the things that look right while reading the wrong four bytes — and because verifying them needs nobody's real cookies. Safari's page table is big-endian while everything inside a page is little-endian; Chromium is AES-128-CBC with an all-spaces IV under PBKDF2-SHA1(password, "saltysalt", 1003), and newer profiles prepend a 32-byte hash of the host *inside* the plaintext, which is dropped when the value doesn't decode as text. What is **not** verified here is the file discovery and a real read: those need the actual browsers, and on this machine reading them is not something to reach for casually.

**More than one account of a provider:**
- [MonitoredAccount.swift](Sources/Pulse/MonitoredAccount.swift) — `AccountKey` is a provider *plus* which of its accounts, and it is what the rail, the store, the cache, the settings panes and the panel's hit testing are all keyed by now. **A provider's first account has the provider's own raw value as its id**, and that is the entire migration strategy: every stored preference — the enabled set, the order, the pinned windows, the routes, and the cached last readings on disk — was written keyed by the provider's raw value, so leaving the first account's key identical means none of it needs converting. There is no migration step, which is the point: making an upgrade look like a fresh install has already cost this app one release.
  Only `.claudeCode` and `.codex` answer `supportsMultipleAccounts`. The rest are read from a login their own tool stored and that store holds exactly one, so a second account of theirs is not something Pulse can be shown however the app is shaped.
- **Why signing in at all, rather than copying what the CLI stored.** Measured: a Codex access token lives 240 hours, a Claude Code one about five. Copying the credential would leave the account you are *not* currently using dead within an afternoon, and the only way to renew it would be with the refresh token the CLI is also relying on — which, if the provider rotates it, signs the user out of their own CLI. Pulse's own login has its own refresh token and touches nothing the CLI owns.
- **Pulse cannot register an OAuth application of its own with either provider**, so [OAuthLogin.swift](Sources/Pulse/OAuthLogin.swift) drives the same public client the provider's CLI uses. Consequences, both stated in Settings: the consent page names the CLI rather than Pulse, and this is not an official integration. Every parameter is read out of the installed CLI rather than remembered — client ids, authorize and token endpoints, the extra query items Codex sends, and which endpoint takes JSON (Anthropic) against a form (OpenAI). A flow with one parameter wrong fails in a way that looks like the user's fault.
  **Grok's device flow is the specification's, and Codex's is not — they share a name and nothing else** (`OAuthLogin.DeviceFlow`). RFC 8628 posts to a code endpoint, then polls the *ordinary* token endpoint until it stops answering `authorization_pending`, and gets tokens straight back. OpenAI's posts to an endpoint of its own, answers with an authorization *code* and the proof key it generated itself, and that code is then exchanged against a redirect address of theirs. Writing either as a special case of the other gives a parser that reads neither reliably, so they are two cases.
  **On the standard flow a refusal and a "still waiting" arrive with the same status.** Both are HTTP 400 and only the body's `error` tells them apart, so the body is read before anything is concluded from the status — measured against xAI with an unapproved code: `400 {"error":"authorization_pending"}`. `slow_down` is an instruction rather than a failure and lengthens the interval by the five seconds the specification names; a client that ignores it is eventually cut off. The poll makes its own request rather than calling `post`, so that "not yet" never travels as a `Failure` the UI would be free to show the user every few seconds while nothing is wrong.
  **xAI does send a pre-filled link, and it is used.** `verification_uri_complete` is the shape of the device-code phishing attack only when the link comes from somebody else — here Pulse asked for the code itself and opens the page itself, so there is no way in, and whether such a link exists at all is the service's own decision: GitHub deliberately sends none, xAI sends one. It is used where offered and never constructed where it is not, the code is still copied and shown for a page that turns out not to fill itself in, and the row's subtitle follows which case it is — telling someone to paste on a page that already filled itself in is an instruction to undo.
  **Grok's parameters come from xAI's discovery document**, `auth.x.ai/.well-known/openid-configuration`, rather than out of the CLI's strings — the same rule one step earlier, since the provider publishes them. The client id is the CLI's and appears in `~/.grok/auth.json` as `oidc_client_id` after any `grok login`. The scopes are `openid email offline_access grok-cli:access`: `grok-cli:access` is what the CLI's own proxy is gated on and `email` is what stops two Grok accounts both being offered as "Grok", while `profile`, `api:access` and the conversation and workspace scopes the CLI also asks for are dropped — the last two would let Pulse read and write the account's chats to draw a percentage. `billing:read` looks like exactly the right scope and is refused: measured, the code endpoint answers `invalid_scope — Scope 'billing:read' is not allowed for this client`. That the remaining four are *enough* was settled by performing the sign-in, not by reasoning about it: an added account reads both endpoints and reports its weekly pool and its plan, so `grok-cli:access` carries the proxy and Codex's widen-the-scopes lesson does not apply here.
  **The redirect flow was not chosen here, and could not be checked either.** Cloudflare answers 403 to anything but a browser on `auth.x.ai/oauth2/authorize`, so whether the client accepts an arbitrary loopback port cannot be probed without performing a sign-in; the device endpoint answers a plain form post, which is how its client and scopes were verified before a line was written. The loopback fields are still filled in from the CLI's own `http://127.0.0.1:<port>/callback` in case that changes.
  **An added Grok account is not told about the CLI's route.** `Provider.soleRoute` names the login the provider's own tool stored, and `fetchAdded` never touches it — so that row is drawn for the primary account only, or it would name a credential the account never uses.
  **Codex is signed in to by device code, not by a redirect** (`codex-rs/login/src/device_code_auth.rs`). `POST /api/accounts/deviceauth/usercode` returns a short code, the user types it at `auth.openai.com/codex/device`, `POST /api/accounts/deviceauth/token` is polled — 403 and 404 both mean "still waiting", which is their convention rather than the specification's `authorization_pending` — and it answers with an authorization code **and the proof key, which the provider generated itself**, to be exchanged against their own `deviceauth/callback` redirect. Nothing is redirected back to this Mac, so there is no local port to collide with the CLI's own sign-in and nothing to keep listening for.
  That is not merely tidier: the redirect flow **does not work here**, and matching it field for field to the published client did not fix it. It ended on OpenAI's own hosted error page — `{"kind":"AuthApiFailure","errorCode":"token_exchange_failed"}` — before the browser ever came back, twice. The loopback code is kept for Claude Code, which has no device flow.
  A sign-in can also fail entirely outside Pulse: the device page asks the user to sign in if the browser has no session, and OpenAI's own hand-off to a Google account came back `token_exchange_failed` there. Pulse's part had already succeeded — the code was on screen — so the remedy is to be signed in at chatgpt.com first, which is what the row's subtitle now says. Worth remembering before reading a provider's error as a bug here.
  **Codex's request matches its published client field for field, and has to.** Asking for a narrower scope than `codex-rs/login/src/server.rs` does — dropping `api.connectors.read` and `api.connectors.invoke`, which looked like good practice — ended the sign-in on OpenAI's own error page reading `token_exchange_failed`, before the browser ever came back. Two other differences were found the same way and fixed: its exchange takes the four fields the specification names and **not** `state` (Anthropic's does take it), and the form body is percent-encoded strictly, since `URLComponents` leaves `:` and `/` alone in a query value and would pass a `+` through to be read back as a space. The Codex CLI is open source; read it rather than inferring from a binary's strings, which is how the first two of these were got wrong.
  Claude Code is asked for `user:profile` alone. Its CLI also asks for inference and session scopes, which would let Pulse **spend** the plan it is only supposed to be reporting on.
- [LoopbackCallback.swift](Sources/Pulse/LoopbackCallback.swift) — the redirect target. **Binding is a separate step from waiting, and has to be**: the port is only known once the listener is ready, and the redirect address goes into the authorize request before the browser is opened. Folding the two together produced a redirect to `localhost:0`. Codex's client is registered for exactly `http://localhost:1455/auth/callback`, so that port is taken or the sign-in fails with something the user can act on; Claude Code's accepts any loopback port. The `state` is checked here rather than by the caller — a redirect not carrying this sign-in's value did not come from it, and it is handed over at `start(expecting:)` rather than at `awaitCode`: the browser can beat that call, and until this sign-in's value is known every arrival is a mismatch.
  **Cancelling has to unwind the wait, not merely mark it cancelled.** A bare `CheckedContinuation` ignores cancellation entirely, and the 300-second timeout sat in an unstructured `Task`, which does not inherit it — so pressing Cancel left the attempt running with its listener still bound, and five minutes later the abandoned one's cleanup cleared the pane and wrote "the browser didn't come back" over the top of a second sign-in the user had since started. `withTaskCancellationHandler` settles it, the cleanup only runs for the attempt still on screen, and `OAuthLogin.post` lets a `CancellationError` through instead of reporting it as the service failing to answer.
  **A busy port does not fail an `NWListener`, it parks it in `.waiting`.** Only `.failed`/`.cancelled` were handled, so a fixed-port sign-in would have hung indefinitely with nothing on screen but a button that had stopped working — unreachable today, since Codex moved to the device flow and Claude Code binds `.any`, but a live trap for the next fixed-port provider. Values are read from the *encoded* query and decoded here, because a query string spells a space `+` and `URLComponents` will not undo that, while decoding before the substitution keeps a literal plus (which arrives as `%2B`) from becoming a space.
- [AccountCredentials.swift](Sources/Pulse/AccountCredentials.swift) / [LocalSecrets.swift](Sources/Pulse/LocalSecrets.swift) — the logins, AES-GCM in `accounts.dat`, owner-only, keyed from the Mac rather than stored. `LocalSecrets` is shared with `APIKeyStore` so there is one copy of the crypto to be right about, with a different derived key per purpose so a box from one store cannot be opened by the other. A file that exists but will not decode is **not** an empty one: saving refuses rather than silently discarding every other account's login. Verified: nothing readable on disk, permissions 600, and a corrupted file refuses both reads and writes.
- `UsageStore.fetchAdded` renews an added account's token when it is close to expiring, because nothing else will — the CLI keeps its own login fresh and this is not that. A renewal that fails reports `.signedOut` rather than a network error: the remedy is the same either way and it is one the user can act on. That case, like every shared one in `Unavailability`, names no provider.

**Localization:**
- English and Simplified Chinese. Strings live in [Sources/Pulse/Resources](Sources/Pulse/Resources) as `en.lproj` / `zh-Hans.lproj` `Localizable.strings`, and `Package.swift` declares `defaultLocalization: "en"` (other languages fall back to it).
- The language follows the system unless the user picks one in Settings, which takes effect **without a relaunch**: `LocalizationSource` swaps in that language's `.lproj` sub-bundle and every lookup reads from it. Because those lookups are a plain function call, SwiftUI has nothing to observe — `SettingsView` and `FloatingUsagePanelView` carry `.id(settings.language)` to force a rebuild. Anything else that caches a localized string needs the same treatment. The same trap is why `UsageWindow.Kind` and `ProviderUsage.Unavailability` are cases rather than stored strings — see below.
- **So do large numbers.** Chinese doesn't group in thousands, so "419M" has to be converted in the reader's head before it means anything; `TokenCount.short` switches to 万 (10⁴) and 亿 (10⁸) when `LocalizationSource.groupsByTenThousands`, giving 4764万 and 4.19亿. The unit characters live in code rather than in the strings file deliberately — they belong to the numeral system, not to the copy, and offering a translator "亿" as text to change invites a mistake.
- **Dates, times and money follow the chosen language too**, via `LocalizationSource.locale` — not `Locale.autoupdatingCurrent`. Picking English and then being told a credit expires "in 22天8小时" is the sort of half-translated seam that reads as unfinished.
- **A `%` next to a placeholder breaks the lookup.** These values are run through `String(localized:)`, so `"%@ · %@% of tokens"` is a malformed printf conversion; bake the sign into the interpolated value instead (`"\(count)%"`).
- **`Scripts/check-localization.sh` gates both halves of that, and the second half exists because of a real escape.** It used to compare only the two `.strings` files to each other, which cannot see a key the *source* asks for and nobody wrote: a find-and-replace renaming `provider` to `account.provider` swept through a **string literal**, and the estimate's caption quietly reverted to English while both `.strings` files went on agreeing with each other perfectly. `Scripts/localization-keys.py` reads the literals with a scanner rather than a pattern — Swift interpolations nest and can contain string literals of their own (`\("\(count)")`), so a regular expression reads half a key — skips comments, and reduces each interpolation to the `%@` that `String.LocalizationValue` produces.
- **Do not put a conditional inside `Text(localized:)`.** `Scripts/localization-keys.py` reads `Text(localized: flag ? "\(x) Left" : "\(x) Used")` as the bare tail — `"Left"` — which happened to match an unrelated key, so the check that exists to catch a missing string reported everything in order while the card fell back to English. Build the string in a property first, where each branch is its own call. The scanner's own blind spot is worth knowing: it wants a string literal immediately after `localized:`.
- **Always go through `String.localized(_:)` or `Text(localized:)`** ([Localization.swift](Sources/Pulse/Localization.swift)). Implicit SwiftUI localization — `Text("Some text")`, `Button("Some text")` — resolves against `Bundle.main`, which for a SwiftPM executable is the bare binary, not the resource bundle holding the `.lproj` folders. It fails silently: the key is shown verbatim, so the app just stays in English and nothing warns you.
- Keys are the English text. For interpolated strings the key is the format with **non-positional** `%@` placeholders (`"%@ used, %@"`), which is what `String.LocalizationValue` generates; writing `%1$@`/`%2$@` in the `.strings` file makes the lookup miss and silently fall back to English.
- SwiftPM lowercases `zh-Hans.lproj` to `zh-hans.lproj` in the built bundle. That is harmless — `Bundle.preferredLocalizations` matches case-insensitively — but it means `Bundle.module.path(forResource: "zh-Hans", ofType: "lproj")` returns nil, which matters only if something looks a table up by name.

**Resources:**
- [Sources/Pulse/Resources](Sources/Pulse/Resources) holds the provider marks as SVG (`claude.svg`, `openai.svg`, `antigravity.svg`, `cursor.svg`, `opencode.svg`, `kimi.svg`, `grok.svg`, `xai.svg`), taken from [Lobe Icons](https://github.com/lobehub/lobe-icons) (`packages/static-svg/icons`, monochrome variants). `LobeIconStore` in [UsageRingView.swift](Sources/Pulse/UsageRingView.swift) loads them once via `Bundle.module`, keyed by `Provider.iconResource`. They are vectors, so one file covers every size drawn; note their `width="1em"` makes `NSImage` report a 1x1 intrinsic size, which is why the store assigns an explicit size and marks them as template images before use. Adding a provider requires: a new `Provider` case, its SVG in `Resources/`, a service that returns a `ProviderUsage`, a branch in `UsageStore.refresh` and `refresh(_:)`, and its answers to `keepsLocalTranscripts` / `hasSourceChoice`. The switches in `AgentActivity.root(for:)` and `UsageLedger.logFiles(for:)` both return an optional root, so an agent with no transcripts opts out there rather than being given a directory that was never going to exist.
